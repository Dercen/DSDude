# Desktop stack recommendation for the DS IDE (research as of 2026-09-24)

## 1. Decision: Electron + Vite + React + TypeScript

**Pick Electron.** Rationale against the alternatives, given the machine (Node 24.16, npm 11.13, .NET 10, Python 3.13, no Rust, no CMake) and the goal (GameMaker-style IDE built by several concurrent Claude Code agents):

| Criterion | Electron 44 + React 19 + Monaco | .NET 10 + Avalonia 12.1.3 + AvaloniaEdit 12.0.0 | Python 3.13 + PySide6 6.11.2 |
|---|---|---|---|
| Code editor quality | Monaco 0.57.0 = the VS Code editor: completion/hover/signature/markers/semantic tokens/folding/minimap built in | AvaloniaEdit is an AvalonEdit port; completion popups, folding exist but no IntelliSense-grade UI; TextMate highlighting via AvaloniaEdit.TextMate | QScintilla or embedding Monaco in QWebEngine (which is Chromium anyway) |
| Canvas editors (sprite/tilemap) | Canvas 2D + PixiJS 8.21.0 (WebGL/WebGPU), OffscreenCanvas, Web Workers | Skia custom controls; workable, less library support | QGraphicsView; adequate, slower iteration |
| Docking panels | dockview 8.3.1 (MIT, serialization, floating, popout) | Dock.Avalonia (good) | QDockWidget (basic) |
| Developer velocity for LLM agents | Highest: TS/React/Vitest have the deepest training coverage; one language (TS) for IDE, compiler, asset pipeline, language service, tests | Good (C#), but two languages if any tooling is scripted; XAML verbose | Good, but packaging (PyInstaller) and typed contracts are weaker |
| Packaging | electron-builder 26.15.3 NSIS + electron-updater 6.8.9 (GitHub Releases) | `dotnet publish` self-contained + WiX/Velopack (extra setup) | PyInstaller/Nuitka, ~150 MB, fragile with Qt plugins |
| Installer baseline | ~90–110 MB (Electron 44 win-x64 zip is 158 MB compressed with deflate; NSIS uses LZMA) | ~70–100 MB self-contained | ~120–180 MB |

Tauri is out (no Rust), and the user's constraint says installing Rust is not justified; nothing in this plan needs it (Vite 8's Rolldown ships as prebuilt binaries, no Rust toolchain needed).

## 3. Monaco integration for the custom language

1. Import the core only: `import * as monaco from 'monaco-editor/esm/vs/editor/editor.api'` (skips TS/JSON/CSS/HTML language bundles). Workers with Vite: `import EditorWorker from 'monaco-editor/esm/vs/editor/editor.worker?worker'; self.MonacoEnvironment = { getWorker: () => new EditorWorker() }` (this is the pattern in Monaco's own `samples/browser-esm-vite-react/src/userWorker.ts`).
2. Register the language: `monaco.languages.register({ id: 'dsdude' })`, `setLanguageConfiguration` (comments, brackets, autoClosingPairs, folding markers, indentationRules, wordPattern), `setMonarchTokensProvider` for immediate syntax colors. Monarch is a declarative regex state machine (`tokenizer: { root: [...], comment: [...], string: [...] }`, `@keywords` lookups, `{ token, next }` actions); it cannot express context-sensitive rules, so plan to add `registerDocumentSemanticTokensProvider` fed by the real lexer/binder later (types vs variables vs built-in functions like `draw_sprite`).
3. Providers, all backed by one `@dsdude/language-service` package (pure TS, no Monaco imports, so the compiler package and tests reuse it): `registerCompletionItemProvider` (triggerCharacters `['.', '(']`; built-ins with snippet insert text, object/room/sprite asset names from the project model, local variables from scope analysis), `registerHoverProvider` (doc strings from a generated built-ins table), `registerSignatureHelpProvider` (triggers `['(', ',']`), `registerDefinitionProvider`, `registerReferenceProvider`, `registerRenameProvider`, `registerDocumentSymbolProvider` (outline), `registerFoldingRangeProvider`, `registerDocumentFormattingEditProvider`, `registerCodeActionProvider`. Diagnostics: run parse+bind in a Web Worker (`comlink` 4.4.2 or a 40-line postMessage RPC) debounced ~150 ms and publish via `monaco.editor.setModelMarkers(model, 'dsdude', markers)`.
4. **LSP vs providers:** Start with providers (phase 1). They are synchronous-friendly, need zero extra packages, and the Monaco API is stable. Wrap the same language-service in `vscode-languageserver` 10.1.1 later (phase 2) to ship a VS Code extension; connecting that server back into the IDE via `monaco-languageclient` 11.0.2 is possible but requires overriding `monaco-editor` with `@codingame/monaco-vscode-editor-api@37.1.0` (its docs say "enforce the correct editor by overrides/resolutions"), ties Monaco to the 0.56-era API, and pulls ~29 `@codingame/*` packages. Keep the service transport-agnostic (`(doc, position) => result` functions) so either wrapper is a thin adapter.

## 4. Sprite editor and room/tilemap editor

- **Sprite editor: raw Canvas 2D.** Pixel art at 8x8–64x64 with 16/256-color palettes is best modelled as `Uint8Array` index buffers per frame plus a BGR555 palette, rendered through `ImageData` into an `OffscreenCanvas` and blitted at zoom with `ctx.imageSmoothingEnabled = false` and CSS `image-rendering: pixelated`. Tools (pencil, fill, line, rect, select/move, mirror, onion-skin, animation strip) are pure functions over the index buffer → trivially unit-testable in Vitest (node env) and undoable via immer patches. No library needed; PixiJS/Konva add nothing here.
- **Room/tilemap editor: PixiJS 8.21.0.** Rooms scroll beyond 256x192 and layer 4 backgrounds + object instances + collision overlays; PixiJS gives GPU batching, `TextureStyle.defaultOptions.scaleMode = 'nearest'`, `roundPixels`, containers per layer, culling, and cheap zoom/pan. Keep the document model in zustand and treat Pixi as a view (`useEffect` diffing tiles by chunk, 32x32-tile chunks as `Mesh`/`TilingSprite`). Use `@vitest/browser-playwright` for tests that need a real WebGL context.
- In-renderer image decode for import/preview: `createImageBitmap(blob, { colorSpaceConversion: 'none', premultiplyAlpha: 'none' })` + `OffscreenCanvas.getImageData` (Chromium decodes PNG/JPEG/GIF/WebP/BMP natively). The deterministic build pipeline uses `pngjs` in Node so `dsdude build` works headless/CI.

## 5. Quantization to DS palettes (JS)

The DS palette space is 15-bit BGR555 (32 levels per channel; entry = `(b << 10) | (g << 5) | r`), 16 colors (4bpp, 16 sub-palettes) or 256 colors (8bpp), with index 0 transparent. Recommended implementation in `@dsdude/asset-pipeline` (~300 lines, zero deps): (1) snap every pixel to RGB555 (`c >> 3`), (2) build a 32x32x32 histogram (32,768 bins), (3) run Wu or median-cut on the histogram for k = 15 or 255 colors (Wu's algorithm is a natural fit for a 5-bit-per-channel cube), (4) optional Floyd-Steinberg (error diffusion) or 4x4 Bayer ordered dithering in 555 space, (5) nearest-palette mapping, (6) pack 8x8 tiles (4bpp: low nibble first) and emit `.bin`/`.h`/`.grf`-style outputs, with shared-palette mode across a sprite group (grit `-pS` semantics). Use `image-q` 4.0.0 as an optional alternative engine and as a cross-check in tests; keep libimagequant out because of its GPL/commercial licence.

## 6. Audio → maxmod

Renderer path (interactive import): `AudioContext.decodeAudioData` (Chromium 152 handles wav/mp3/ogg/flac/aac/opus) → `OfflineAudioContext(1, n, targetRate)` to downmix/resample to 8–22.05 kHz mono → `wavefile.fromScratch(1, rate, '16', Int16Array)` (+ `wav.smpl.loops` for loop points) → write WAV → `mmutil -d -o soundbank.bin -h soundbank.h *.wav *.xm`. Headless path (CLI/CI): `@audio/decode` 3.15.0 + `@alexanderolsen/libsamplerate-js` 2.1.2 (or a small windowed-sinc resampler). Trackers (MOD/S3M/XM/IT) pass straight through to mmutil.

## 7. Spawning builds and the emulator, streaming logs

- Run the build orchestrator in `utilityProcess.fork()` (Electron's Node child with MessagePort, `stdio: 'pipe'`, `serviceName`) so a hung compiler or a cancelled job never blocks the main process; inside it use `child_process.spawn(exe, args, { windowsHide: true, env: { ...process.env, LM_LICENSE_FILE }, timeout })`. **mwccarm hangs silently without `LM_LICENSE_FILE`** (verified earlier by the orchestrator), so the driver must set it, enforce per-translation-unit timeouts (~120 s), and turn a timeout into a readable diagnostic.
- Split stdout/stderr on newlines, batch to the renderer every ~16–33 ms over `webContents.send('build:log', { jobId, lines })` (or a transferred `MessagePort`), parse `file:line: error:` patterns into Monaco markers and a Problems panel.
- Cancel: `tree-kill` 1.2.2 for the make → mwccarm → mwldarm tree. For the emulator prefer a graceful `taskkill /PID <pid>` (WM_CLOSE) then `/F` after ~2 s so it flushes save files.
- Windows gotcha: never spawn `.cmd`/`.bat` without `shell: true` (Node's CVE-2024-27980 hardening); call the `.exe` directly.
- Emulator CLIs (verified from source and bundled README): DeSmuME 0.9.13: `DeSmuME_0.9.13_x64.exe "game.nds"` with `--windowed-fullscreen`, `--start-paused`, `--num-cores`, `--load-slot=N`, `--arm9gdb=PORT` (GDB stub for a future debugger). melonDS 1.1 (2025-11-18, GPL-3, 19.5 MB win-x86_64 zip): `melonDS.exe game.nds`, `-f/--fullscreen`, `-b/--boot auto|always|never`; firmware boot needs a BIOS dump, direct boot of homebrew does not. Recommendation: make the emulator path configurable, default to melonDS (actively maintained, more accurate), and support DeSmuME since it is already downloaded (38.3 MB exe).

## 8. File watching

`chokidar` 5.0.0 in the main/utility process for the project tree (ignore `build/`, `.git`), forwarding coalesced events to the renderer for the asset browser and external-edit detection. Node 24's `fs.watch({ recursive: true })` is documented as platform-dependent ("only on supported platforms"); chokidar removes that variance and has no native dependency.

## 9. Electron security defaults and typed IPC

- Defaults already right in Electron 44: `nodeIntegration` off (since 5), `contextIsolation` on (since 12), `sandbox` on (since 20), `webSecurity` on. A sandboxed preload's `require` is a polyfill limited to `electron`, `events`, `timers`, `url` and the preload must be a single bundled file (electron-vite does this). Keep `apps/ide/package.json` **without** `"type": "module"` so electron-vite emits CJS main+preload; an ESM preload would force `sandbox: false` (electron-vite docs: ESM preload "must be unsandboxed and end with .mjs"). Bundle ESM-only main-process deps (chokidar 5, execa 10) with `build.externalizeDeps.exclude`.
- Add a CSP `<meta>` (`default-src 'self'; worker-src 'self' blob:`), `setWindowOpenHandler` denying everything except dockview popouts, validate `event.senderFrame.url` in every handler, load the renderer via a custom `app://` protocol in production rather than `file://`.
- Fuses via electron-builder's `electronFuses` block for release builds only: `runAsNode: false, enableCookieEncryption: true, enableNodeOptionsEnvironmentVariable: false, enableNodeCliInspectArguments: false, enableEmbeddedAsarIntegrityValidation: true, onlyLoadAppFromAsar: true, grantFileProtocolExtraPrivileges: false`.
- **IPC: hand-rolled zod contract, not tRPC.** `packages/ipc-contract` exports a channel map `{ 'project.open': { input: z.object({ path: z.string() }), output: ProjectSchema }, ... }` plus event schemas. Preload exposes only `invoke(channel, payload)` and `on(channel, cb)` for known channels (callbacks never receive the `event`), main wraps `ipcMain.handle` with `schema.input.parse` and sender validation, and the renderer gets a fully typed client via `z.infer`. tRPC 11.19.0 itself is fine, but every Electron adapter is stale: `electron-trpc` 0.7.1 (2024-12-07, tRPC 10 era), `trpc-electron` 0.1.2 (2025-01-06), `electron-trpc-experimental` 1.0.0-alpha.1 (2025-06-18).

## 10. Packaging

electron-builder 26.15.3, `win.target: nsis` x64 only, `compression: "maximum"`, `asar: true` (smartUnpack unpacks .exe/.node automatically), `extraResources: [{ from: "vendor/toolchain", to: "toolchain" }, { from: "vendor/emulator", to: "emulator" }]` → available at `path.join(process.resourcesPath, 'toolchain')`. NSIS options: `oneClick: false, perMachine: false, allowToChangeInstallationDirectory: true`. Auto-update: electron-updater 6.8.9 with the GitHub Releases provider; only NSIS supports auto-update on Windows; unsigned builds work but trip SmartScreen (code signing is a later decision). Size budget: Electron 44.4.5 win32-x64 zip is 158,184,819 bytes (deflate); after LZMA the bare IDE installer should land around 90–110 MB; ship only `mwccarm/2.0/sp1` (5 MB) + `1.2/license.dat`, `dsd` (8.1 MB), optional devkitARM binutils (9 MB), melonDS (19.5 MB) → roughly +35–45 MB. Do not ship the whole 64 MB `mwccarm` tree. Note: mwccarm is proprietary Metrowerks/Nintendo software; a "locate existing toolchain" option and the open BlocksDS path (v1.16.0, 2025-12-25; Windows via Wonderful Toolchain `wf-pacman -S blocksds-toolchain`) hedge that risk.

## 11. Monorepo for concurrent Claude Code instances

Use **npm workspaces** (npm 11.13.0 already installed, lockfile v3; electron-builder's default hoisted layout). pnpm 12.6.0 is available via corepack 0.35.0 (`corepack use pnpm@12.6.0`) and has nicer `catalog:` pinning, but electron-builder with `nodeLinker: hoisted` workspaces currently has an open nested-version bug (#10228; fix PR #10234 still a draft on 2026-09-24). Layout:

```
dsdude/
  package.json            workspaces: ["apps/*","packages/*","tools/*"]; root scripts only
  tsconfig.base.json      biome.json   vitest.workspace.ts
  apps/ide/               @dsdude/ide   electron-vite: src/main, src/preload, src/renderer (React, dockview, Monaco, PixiJS)
  packages/lang/          @dsdude/lang  lexer, parser, AST, binder, diagnostics, formatter (zero deps)
  packages/language-service/ @dsdude/language-service  completion/hover/signature/symbols over @dsdude/lang, transport-agnostic
  packages/compiler/      @dsdude/compiler  AST→C codegen + build driver (mwccarm/mwldarm/dsd invocation, LM_LICENSE_FILE, timeouts), CLI `dsdude build`
  packages/asset-pipeline/ @dsdude/asset-pipeline  PNG→tiles/palettes (RGB555 quantizer), audio→WAV→mmutil, fonts, tilemaps
  packages/project-format/ @dsdude/project-format  zod schemas for project/room/object/sprite JSON, load/save, migrations, sample projects
  packages/ipc-contract/  @dsdude/ipc-contract  channel map + zod schemas shared by main/preload/renderer
  packages/lsp-server/    (phase 2) vscode-languageserver wrapper + VS Code extension
  runtime/                C engine for the DS (objects, rooms, sprites, input, maxmod audio); Makefile-driven; no npm
  tools/                  tsx scripts, golden fixtures
  vendor/                 mwccarm (2.0/sp1 + license), dsd, binutils, emulator (gitignored or LFS)
```

Ownership rules that avoid merge conflicts: each package owns its `package.json`, `tsconfig.json`, `vitest.config.ts`, `CLAUDE.md`; cross-package APIs are the exported types in `src/index.ts` plus `@dsdude/ipc-contract` and `@dsdude/project-format` schemas (designed first, changed only by the owning agent); root files (`package-lock.json`, `biome.json`, `tsconfig.base.json`) are owned by an infra agent; other agents add deps only inside their own package and run `npm install` from the root once. One git worktree per agent (Claude Code's EnterWorktree), Biome formatting on commit so diffs stay semantic, Vitest golden tests (`script.ds → expected.c`, `sprite.png → expected.bin`) as the contract between the compiler, asset and IDE teams.


## Recommendations
- Adopt Electron 44.4.5 + Vite 7.3.6 + electron-vite 5.0.0 + React 19.3.0 + TypeScript 7.0.2 (type-check only) as the IDE stack; revisit Vite 8.3.1 when electron-vite 6 leaves beta (still 6.0.0-beta.1 with open Rolldown bugs), or use vite-plugin-electron 1.1.2 if Vite 8 is needed now.
- Integrate monaco-editor 0.57.0 directly (import 'monaco-editor/esm/vs/editor/editor.api', Vite '?worker' for editor.worker) with a thin React wrapper; skip @monaco-editor/react (CDN loader by default).
- Implement the language tooling as Monaco providers (completion/hover/signature/definition/symbols/format) backed by a pure-TS @dsdude/language-service running in a Web Worker; defer a real LSP (vscode-languageserver 10.1.1) to phase 2 for a VS Code extension, and avoid monaco-languageclient 11.0.2 in the IDE because it forces the @codingame/monaco-vscode-editor-api 37.1.0 override.
- Build the sprite editor on raw Canvas 2D over Uint8Array index buffers + BGR555 palettes (pure functions, Vitest-testable); build the room/tilemap editor on PixiJS 8.21.0 with scaleMode 'nearest' and chunked tile meshes; do not adopt Konva.
- Write the DS quantizer in-house in @dsdude/asset-pipeline (snap to RGB555, 32x32x32 histogram, Wu/median-cut to 15 or 255 colors, index 0 transparent, optional Floyd-Steinberg/Bayer dithering, 4bpp/8bpp tile packing); keep image-q 4.0.0 as an optional engine/cross-check and avoid libimagequant (GPL/commercial).
- Decode/resample audio in the renderer with AudioContext.decodeAudioData + OfflineAudioContext, encode 8/16-bit PCM WAV with wavefile 11.0.0 (including smpl loop chunks), and feed mmutil -d; use @audio/decode 3.15.0 + libsamplerate-js 2.1.2 for headless CLI builds; do not bundle ffmpeg-static (GPL, ~100 MB).
- Run builds in utilityProcess.fork with child_process.spawn({ windowsHide: true, env: { LM_LICENSE_FILE }, timeout }), stream line-batched logs over IPC/MessagePort, cancel with tree-kill 1.2.2, and stop the emulator gracefully with taskkill before /F.
- Type IPC with a zod 4.6.5 channel-map contract package (invoke/on exposed through contextBridge, sender validation + schema parse in main); do not use electron-trpc or its forks (all stale since 2024-2025).
- Keep Electron security defaults (sandbox, contextIsolation, no nodeIntegration), keep the app package CJS so the sandboxed preload stays CJS, add CSP and setWindowOpenHandler, and enable electron-builder's electronFuses block only for release builds (Playwright needs nodeCliInspect).

## Open questions
- Will electron-vite 6.x reach a stable release soon (it has been at 6.0.0-beta.1 since 2026-04-12)? If not within the project's first milestone, decide between staying on Vite 7.3.6 or switching to vite-plugin-electron 1.1.2 for Vite 8.
- Licence/redistribution of mwccarm (proprietary Metrowerks/Nintendo) inside an installer: should the IDE ship it, require the user to locate an existing copy, or move the runtime to BlocksDS (v1.16.0) as the open toolchain? This drives installer size and the compiler package's build driver.
- IDE licence: MIT/Apache keeps libimagequant (GPL) and ffmpeg-static (GPL) out; if the IDE will be GPL-3 anyway, libimagequant-wasm 0.3.0 becomes the best-quality quantizer option.
- Which emulator to bundle by default: melonDS 1.1 (GPL-3, 19.5 MB, more accurate, needs no BIOS for direct boot of homebrew) vs the already-downloaded DeSmuME 0.9.13 (38 MB, 2022 stable). Also whether GDB-stub debugging (both emulators expose it) is in scope for a later milestone.
- Does any tool in the pipeline need the TypeScript compiler API (typescript-eslint, vite-plugin-dts, ts-morph)? If yes, pin @typescript/typescript6 6.0.2 alongside typescript 7.0.2 using the alias trick; if only Biome + tsc are used, TS 7.0.2 alone suffices.
- Should the language service run in a Web Worker in the renderer (recommended) or in a utilityProcess with an LSP transport from day one? The latter costs more now but avoids a second integration later if a VS Code extension is a firm goal.
- Dockview popout windows call window.open; confirm the setWindowOpenHandler allow-list and CSP still permit them under sandbox before committing to popouts in the panel design.
- Whether the electron-builder pnpm hoisted-workspace fix (PR #10234) lands; if so pnpm 12 with catalogs becomes attractive for version pinning across many agent-owned packages.
