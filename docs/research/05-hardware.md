# Nintendo DS constraints for a GameMaker-like runtime, and the script-execution strategy

## 1. The machine, in numbers (GBATEK unless noted)

**CPUs.** ARM946E-S ("ARM9", ARMv5TE, no FPU, no branch predictor, 5-stage pipeline) at 33.513982 MHz x 2 = **67.03 MHz**; ARM7TDMI at **33.51 MHz**. GBATEK DS Technical Data: "NDS9: 66MHz, NDS7: 33MHz". ARM946E-S is rated **1.14 DMIPS/MHz** (design-reuse Cortex-R4 vs ARM9E comparison), so about **76 DMIPS** total, and only when running from TCM/cache. DSi-mode ARM9 runs 2x (**134 MHz**) with 16 MB RAM; TWiLight Menu can force the TWL clock even for DS-mode homebrew, but DS Lite/Phat users get 67 MHz, so budget for 67.

**Tightly coupled memory and caches.** ITCM **32 KB** (BlocksDS maps it at 0x01000000 to keep NULL unmapped), DTCM **16 KB** (BlocksDS: 0x02FF4000, holds the ARM9 stack), I-cache **8 KB**, D-cache **4 KB**, 4-way, **32-byte lines**, read-allocate (writes do not allocate). Only the ARM9 sees TCM; **DMA cannot touch ITCM/DTCM**.

**Memory timings (GBATEK "DS Memory Timings", units are 33 MHz cycles, so multiply by 2 for ARM9 cycles).**
- TCM / cache hit: 0.5 -> **1 ARM9 cycle**.
- Main RAM, NDS9 data: N32 = 10, S32 = 2 -> **20 ARM9 cycles for a non-sequential 32-bit load, 4 for sequential**. Code fetch: N32 = 9 and S32 = 9 (opcode fetch is "always N32 + 3 waits").
- **Cache miss to main RAM: 23 units = 46 ARM9 cycles per 32-byte line**; miss to BIOS 11.
- GBATEK's own summary: the "66MHz" NDS9's "effective bus speed is barely about 8..16MHz"; the real 66 MHz exists only for cache/TCM hits. A 3-wait penalty hits every non-sequential access except cache, TCM and (partly) main RAM.
- Design consequence: the interpreter loop and the hottest builtins must live in ITCM (libnds `ITCM_CODE`), the active VM register file and stack in DTCM, and instance data must be laid out contiguously so the 4 KB D-cache streams it.

**RAM.** Main RAM **4 MB** (DSi 16 MB); BlocksDS reserves the **last 48 KB** (bootstub, exception handlers, IPC, user settings). Shared WRAM 32 KB + ARM7-only WRAM 64 KB. Practical budget for a game after a ~0.4-0.7 MB runtime binary (libnds + maxmod + VM + ARM7 binary): **about 3.0-3.3 MB**.

**Frame timing (GBATEK "DS Video Stuff").** Dot clock 5.585664 MHz (33.513982/6); 355 dots/line (256 visible + 99 blank) at 15.7343 kHz; 263 lines (192 visible + 71 blank) at **59.8261 Hz**. Therefore:
- **1,120,380 ARM9 cycles per frame** (263 x 355 x 6 x 2).
- **VBlank = 71 lines = 302,460 ARM9 cycles (27% of the frame)**: this is the safe window for OAM copies, VRAM uploads, map ring-buffer updates.
- HBlank per line = 99 dots = 1,188 ARM9 cycles; one visible line = 1,536 33-MHz cycles.

**Screens and 2D engines.** Two 256x192 LCDs, 18-bit color out, 15-bit (BGR555) palette entries. Two 2D engines (A = "main", B = "sub"), each with **4 BG layers** and 6/7 modes:

| Mode | BG0 | BG1 | BG2 | BG3 |
|---|---|---|---|---|
| 0 | Text/3D | Text | Text | Text |
| 1 | Text/3D | Text | Text | Affine |
| 2 | Text/3D | Text | Affine | Affine |
| 3 | Text/3D | Text | Text | Extended |
| 4 | Text/3D | Text | Affine | Extended |
| 5 | Text/3D | Text | Extended | Extended |
| 6 (A only) | 3D | - | Large bitmap | - |

Engine B: no 3D, no mode 6, BG0 always Text. Text layers: 16- or 256-color tiles, up to **1024 tiles** per layer, maps 256x256 .. 512x512 px (rooms bigger than 512 px need the standard scrolling ring-buffer trick: rewrite the 32x32-tile edge as the camera moves, a few dozen halfword writes per frame). Extended layers: 16-bit-map rot/scale (256-color text+affine), 256-color bitmap, direct-color bitmap; rot/scale maps 128x128 .. 1024x1024. "Bitmaps that require more than 128K VRAM are supported on engine A only."

**VRAM.** 9 banks, **656 KB** total: A/B/C/D = 128 KB, E = 64 KB, F/G = 16 KB, H = 32 KB, I = 16 KB. Allowed uses: A,B -> main BG, main OBJ, textures; C -> main BG, sub BG, textures; D -> main BG, sub OBJ, textures; E -> main BG, main OBJ, textures, tex-palette, ext-palettes; F,G -> main BG, main OBJ, tex-palette, ext-palettes; H -> sub BG, ext-palettes; I -> sub BG, sub OBJ, ext-palettes. **Maximum mappable: main BG 512 KB, main OBJ 256 KB, sub BG 128 KB, sub OBJ 128 KB.** A sane default for a GameMaker-like runtime: A = main OBJ (128 KB), B = main BG (128 KB), C = sub BG (128 KB), D = sub OBJ (128 KB), E = main BG (second 64 KB, or textures), F/G = main BG/OBJ extended palettes, H = sub BG ext palette, I = sub OBJ ext palette. That gives 128 KB of sprite graphics per screen (256 frames of 32x32 256-color, or 512 frames of 16-color) and 128-192 KB of tile/map data per screen.

**Sprites (OAM).** **128 OBJs per engine**, 12 sizes: 8x8, 16x16, 32x32, 64x64, 16x8, 32x8, 32x16, 64x32, 8x16, 8x32, 16x32, 32x64 (libnds `SpriteSize_*`). **32 affine parameter sets** per engine (so at most 32 rotated/scaled sprites per screen, and double-size mode is needed to avoid clipping). Color formats: 16-color, 256-color, and DS-only **16-bit bitmap sprites** with per-sprite alpha. 1D tile mapping boundaries 32/64/128/256 bytes (libnds `SpriteMapping_1D_32..256`; use `_1D_128` or `_1D_256` to address the full 128-256 KB), bitmap mapping 128/256-byte or 2D 128/256-px wide. OAM is 1 KB per engine (128 x 8 bytes); libnds keeps a shadow OAM and `oamUpdate()` DMA-copies it during VBlank. Per-scanline sprite budget: GBA's rule is 1,210 cycles per line, 1 cycle per normal-sprite pixel and 10+2n per affine sprite; GBATEK gives no separate DS figure, so treat "about 1,200 sprite pixels on any one scanline" as the conservative limit (e.g., 19 sprites 64 px wide, or ~75 16-px sprites on one line) beyond which sprites vanish.

**Palettes.** Per engine: 512 B BG + 512 B OBJ standard palette RAM (256 x 15-bit colors = 16 palettes of 16 colors, or one 256-color palette). Extended palettes: **BG 32 KB per engine (4 slots x 8 KB = 16 x 256-color palettes per layer)** and **OBJ 8 KB per engine (16 x 256-color palettes)**; OBJ extended palettes must sit in VRAM F, G or I. With extended palettes every 256-color sprite/layer can carry its own palette, which is the closest thing to GameMaker's "just import a PNG" workflow.

**3D engine (engine A only).** Polygon RAM 104 KB / Vertex RAM 144 KB = **2,048 polygons and 6,144 vertices per frame**; textures from any of A-E (up to 512 KB), per-polygon alpha, toon shading, fog; vertices are 4.12, matrices 20.12 fixed point (libnds `v16`/`f32`). MicroLua used the 3D engine as a sprite renderer to get unlimited rotate/scale/alpha/tint on the main screen; the cost is that it is main-screen only (or 30 fps per screen via display capture).

**DMA.** 4 channels per CPU (8 total); NDS9 start modes: immediate, VBlank, HBlank, display start, main-memory display, cartridge, GXFIFO; 21-bit word counts. Cannot access TCM.

**Cartridge / NitroFS.** ROMCTRL clock = 33.51 MHz / 5 = **6.7 MHz** (or /8 = 4.2 MHz) over an 8-bit gamecard bus, so a peak of about **6.7 MB/s** (Copetti: "up to 6.7 MB/s") minus KEY1 gaps (BIOS minimum gap1 0x8F8, gap2 0x18 per 512 B). That number only applies to official carts and to emulators; BlocksDS' NitroFS tutorial confirms emulators and official carts "behave just like official games", while **on flashcarts NitroFS is just `fopen` of the .nds on the SD card through DLDI**, needing `argv[0]` from the loader (use the Homebrew Menu / TWiLight Menu). I found no citable KB/s table for DLDI; community reports put good flashcarts at low single-digit MB/s and old ones well below 1 MB/s, and DSi SD via BlocksDS' profi200 DMA driver notably faster. Plan room loads for ~1 MB/s worst case: a 200 KB room (tiles, maps, sprite frames, palettes) is ~0.2 s on a slow cart and effectively instant on DeSmuME. Use large `fread`s (whole files) and `DC_FlushRange` before any DMA copy.

**Sound.** 16 hardware channels mixed by the ARM7: PCM8, PCM16, IMA-ADPCM on all, PSG rectangle on 8-13, noise on 14-15; 128 volume steps, 128 pan positions, timer = -(33513982/2)/freq, loop modes manual/infinite/one-shot; 32 kHz 10-bit DAC output. Only the ARM7 can touch the sound registers (libnds sends FIFO commands). Maxmod (BlocksDS mirror) offers hardware mode (16 ch, minimal ARM7 CPU), interpolated mode, and extended software mixing up to 30 channels; formats MOD/XM/IT/S3M plus WAV effects; `mmInitDefault("nitro:/soundbank.bin")` loads modules/samples on demand into main RAM via `mmLoad`/`mmLoadEffect`, `mmEffectEx` takes rate (6.10 fixed point, 1024 = original pitch), volume 0-255, panning 0-255; `mmStreamOpen` for streamed music. Sample memory cost: 8-bit 16 kHz = 16 KB/s, ADPCM halves it.

## 2. Measured on this machine (mwccarm 2.0/sp1 and MSYS2 gcc 15.2)

I compiled a 10-opcode register VM (`switch` dispatch, 20.12 registers) with `mwccarm -proc arm946e -O4,s -nostdinc` and disassembled it with `arm-none-eabi-objdump`. The generated dispatch is a double jump (`addls pc,pc,r0,lsl#2` into a table of `b` instructions). Pricing the OP_ADD path with the ARM9E-S cycle table (Sloss/Symes/Wright Table B3.9: ALU 1, ALU with pc destination 3 (+1 if shifted), B 3, LDR 1 plus a 1-cycle use interlock and +1 for a shifted offset, LDR pc 5, STR 1 (+1 shifted), SMULL 3):
- dispatch: `ldr ip,[r9],#4` (2 incl. interlock) + 7 ALU (7) + `addls pc` (4) + `b handler` (3) = **16 cycles**
- body: 2 shifted `ldr` (2 + 3 with interlock) + `add` (1) + shifted `str` (2) + `b loop` (3) = **11 cycles**
- **~27 cycles per simple op, ~31 for a 20.12 multiply (smull/lsr/orr)** when code is in ITCM/I-cache and data in DTCM/D-cache.

That is **2.5 M ops/s = ~41,000 VM ops per frame at 100% CPU**. A GCC computed-goto (threaded) dispatch replicated at the end of each handler is 5-6 instructions plus one 3-5-cycle pipeline flush, roughly **11 cycles of dispatch, ~19 per ADD: 3.5 M ops/s, ~59,000 ops/frame**; direct-threaded (handler addresses patched into the code stream at load) saves 2-4 more. Thumb is the wrong mode for this loop: `-thumb` grew the same function from 77 to 120 instructions. Straight-line bytecode in main RAM costs an extra ~46 cycles per 32-byte line (8 ops) on D-cache misses, i.e. ~6 cycles/op amortized; loops stay resident. Cross-check: 76 DMIPS / ~25 native instructions per VM op gives the same ~3 M ops/s.

Compile latency (Strategy A): a 7,003-line, 498 KB C file emulating 200 transpiled step events took **2.40 s** with mwccarm -O4,s (0.33 MB object), **1.0 s** split into 20 files over 16 cores, and **0.07-0.08 s** warm (1.1 s cold) with x86-64 gcc -O2 as a proxy for arm-none-eabi-gcc's front end; one 35-line function takes 0.14 s / 0.07 s. So a GCC-based rebuild of a mid-size project would be about 1-3 s plus link + `ndstool` + asset conversion; latency is not the deciding factor.

GBVM floor: 16 contexts (`VM_MAX_CONTEXTS`), 64-word stacks, 768-word heap, `INSTRUCTIONS_PER_QUANT = 16`, and `process_VM()` keeps calling `script_runner_update()` while it returns `RUNNER_BUSY`, so scripts run to their next `VM_IDLE` within the frame; the quantum is fairness, not a per-frame cap. On a 4.19 MHz SM83 (~70K cycles/frame) that is a few hundred VM ops per frame at most, and GB Studio games are entirely playable. The DS VM has 50-100x that budget.

## 3. Strategy comparison

**A. Transpile to C + GCC on every Play.** Best runtime speed (`x += hspeed` is 4-5 cycles native vs ~27 interpreted, though scripts dominated by builtin calls narrow that to 2-3x). Costs: every end-user of the IDE must install BlocksDS/devkitARM (hundreds of MB, PATH/MSYS2 setup: exactly the thing a beginner-oriented tool should hide); `#line` mapping only covers compiler errors, while runtime faults become ARM exceptions with no script context; no live variable inspection; `mwccarm` cannot fill the role (proprietary FlexLM-licensed Nintendo/Metrowerks tool that cannot be redistributed, and it cannot build against libnds' GCC-specific headers), so the toolchain would have to be BlocksDS anyway.

**B. Bytecode VM in a prebuilt `runtime.nds`, project packed into NitroFS at Play time.** Play = compile scripts to bytecode (milliseconds), convert changed assets, run `ndstool -c game.nds -7 arm7.elf -9 arm9.elf -d nitrofs/` (sub-second for tens of MB), launch `DeSmuME_0.9.13_x64.exe game.nds` (positional ROM path; the binary also exposes `--load-slot`, `--start-paused`, `--console-type`, `--num-cores`, `--disable-sound`, `--frameskip`, `--windowed-fullscreen`, `--slot1-fat-dir`; melonDS likewise takes the ROM path and `-f`). No compiler on the end-user machine; runtime errors carry script/line numbers; a debug build can expose watch/step over the emulator's memory. Cost: 2.5-3.5 M ops/s ceiling; hot paths must be native.

**C. Hybrid.** B for iteration, A as an optional "release" export for users who install BlocksDS. Doubles the surface area (two backends must agree on semantics), and the speed gain matters only for arithmetic-heavy scripts.

**Budget check for B.** Reserve ~50% of the frame (560K cycles) for scripts: ~20K ops (switch) to ~29K ops (threaded) per frame. A typical GameMaker step event (a few conditionals, some fixed-point math, 2-4 builtin calls) compiles to 30-80 ops, so **250-700 instances with step events per frame at 60 fps, or 100-200 instances with generous headroom**, and the sprite hardware caps visible instances at 128 per screen anyway. Event dispatch overhead is ~50-100 cycles per invocation (set `self`/`other`, register base, PC); 200 instances x 3 events = ~60K cycles = 5% of the frame. Native (C) must own: collision (uniform-grid broadphase, AABB/circle narrow phase; per-pixel masks opt-in), movement integration (`x += hspeed` for all instances in one native loop), OAM shadow building, BG scrolling/map ring buffers, animation stepping, alarms, sound FIFO, NitroFS loading, trig/sqrt/div (hardware divider and sqrt units via libnds `div32/divf32/sqrtf32`), and string formatting.

## 4. Runtime data design for a 67 MHz, no-FPU, 4 MB machine

- **Real = 32-bit signed 20.12 fixed point** (range +-524,288, resolution 1/4096 = 0.000244). Rationale: it is libnds' `f32`/3D hardware format, so `sinLerp/cosLerp` (4.12 out, 32768 angle units per turn), `divf32`, `sqrtf32`, `mulf32` all drop in; positions up to 500K px cover any tilemap; speeds like 0.1 px/frame are 0.1% off (0.06 px/s drift, invisible). 16.16 gives finer fractions but only +-32,768 range and overflows in products sooner; 24.8 is too coarse for slow speeds. Multiply with `smull` + shift (3+2 cycles, 64-bit intermediate, so no overflow until the result exceeds 20.12). Expose `degrees` in scripts and convert to 32768-unit angles at the boundary; `sinLerp` returns 4.12, shift left 8 to get 20.12. Never NaN-box: no FPU means every double op is a 100+-cycle libgcc call.
- **Value cell: 8 bytes {u32 tag; s32 payload}**, kinds real/int/bool/undefined/string/array/instance-id/asset-id. Registers and stack in DTCM (32 registers x 8 B = 256 B per context). Declared instance variables with an inferred `real` type can be stored untagged (4 B) when the compiler proves the type.
- **Instances**: compile-time slot layout per object (built-ins x, y, hspeed, vspeed, image_index, image_speed, image_xscale, image_yscale, image_angle, image_alpha, depth, visible, alarm[12], sprite_index, mask_index, object_index, persistent = ~24 slots) plus declared vars; fixed-size 256-byte blocks in one pool (**512 blocks = 128 KB**; hard cap 1,024) iterated as a contiguous array for D-cache friendliness; a lazily allocated 8-entry open-addressing overflow map (64 B from a small pool) for undeclared/dynamic names, keyed by interned symbol id. Object inheritance via parent slot layouts (child appends).
- **Strings**: all identifiers and literals interned at compile time (symbol id = 16-bit); runtime strings immutable, ref-counted, size classes 16/32/64/256 B from a 64-128 KB arena; concatenation is the only allocating op most games use.
- **Memory map (4 MB)**: runtime binary 0.4-0.7 MB; bytecode + constant pool 20-300 KB; instance pool 128 KB; string/array heap 128-256 KB; **room arena 1-1.5 MB** (bump allocator reset on room change: decoded tiles/maps/masks, staged sprite frames); maxmod samples/modules 0.5-1 MB; ~300 KB slack. Everything is fixed-capacity and reported in the IDE ("Room memory 812 KB / 1,536 KB").
- **VRAM plan** as in section 1; sprite frames for a room are preloaded into OBJ VRAM at room start (a 64-frame 32x32 256-color character = 64 KB); frames beyond the 128 KB/screen budget are streamed by DMA during VBlank (302K cycles is enough for tens of KB per frame).

## 5. Verdict

**Strategy B, built with GCC (BlocksDS) as the runtime toolchain, threaded dispatch in ARM mode in ITCM, 20.12 fixed point.** It is the only option that gives a beginner a Play button with no toolchain install, the numbers show it comfortably runs hundreds of scripted instances at 60 fps on real hardware, and it enables script-level error messages and debugging. Keep the bytecode format and native-builtin ABI stable so a later "export via transpile" (Strategy C) is an additive, optional backend rather than a redesign. The `dsd` decomp tool and `mwccarm` in the project folder are not useful for this pipeline (mwccarm cannot link libnds and cannot ship with the IDE), beyond serving as a local ARM code-size/cycle inspection tool as used above.

## Recommendations
- Adopt Strategy B: a prebuilt runtime.nds (ARM9+ARM7 ELFs built once with BlocksDS/GCC) containing a bytecode VM; 'Play' compiles scripts to bytecode, converts changed assets, runs ndstool -c game.nds -7 arm7.elf -9 arm9.elf -d nitrofs/, and launches DeSmuME_0.9.13_x64.exe game.nds (positional ROM path; optional --start-paused, --num-cores, --windowed-fullscreen). No compiler is needed on end-user machines.
- Do not use mwccarm or dsd in the build pipeline: mwccarm is proprietary (FlexLM license.dat), cannot compile libnds/BlocksDS headers, and cannot be redistributed with the IDE; dsd is a retail-ROM decompilation tool. Keep mwccarm only as a local ARM code-size/cycle inspection tool.
- Implement the VM as a register machine with 32-bit instruction words (op:8, a:8, b:8, c:8), GCC computed-goto (threaded) dispatch replicated per handler, compiled in ARM mode (not Thumb) and placed in ITCM (ITCM_CODE) with the active context's registers/stack in DTCM. Expect ~19-27 cycles per simple op: 2.5-3.5 M ops/s, 40-60K ops per 1,120,380-cycle frame.
- Budget 50% of the frame for scripts (about 20-29K VM ops), which supports 250-700 instances with step events; make everything below that line native C: collision broadphase (uniform grid) and AABB/circle narrow phase, movement integration, OAM shadow building, BG scrolling ring buffers, animation/alarm stepping, sound FIFO, NitroFS loading, trig/div/sqrt via libnds LUT and hardware divider.
- Represent 'real' as 32-bit signed 20.12 fixed point (libnds f32): +-524,288 range, 1/4096 resolution, smull-based multiply, divf32/sqrtf32 on the hardware units, sinLerp/cosLerp (32768 units per turn, 4.12 out, shift left 8). Expose degrees in the script language and convert at the boundary. Never NaN-box or use doubles (no FPU; libgcc soft-float is 100+ cycles per op).
- Use an 8-byte tagged value cell {u32 tag; s32 payload}; give each object a compile-time slot layout (about 24 built-in slots plus declared vars, parent layouts prepended) in fixed 256-byte instance blocks from a single contiguous pool (default cap 512, hard cap 1,024), plus a lazily allocated 8-entry overflow hash map for undeclared variables keyed by interned symbol id.
- Intern all identifiers and string literals at compile time (16-bit symbol ids); runtime strings immutable and ref-counted in a 64-128 KB size-class arena. Make every runtime allocator fixed-capacity (room bump arena ~1-1.5 MB reset on room change, instance pool, string heap, maxmod sample budget ~0.5-1 MB) and surface usage meters in the IDE, since only ~3.0-3.3 MB of the 4 MB is available.
- Default VRAM allocation: A = main OBJ, B = main BG, C = sub BG, D = sub OBJ, E = extra main BG or textures, F/G = main extended palettes, H = sub BG extended palette, I = sub OBJ extended palette; enable extended palettes so each 256-color sprite/layer carries its own palette (16 x 256 colors per engine for OBJ). Preload a room's sprite frames into the 128 KB per-screen OBJ VRAM at room start and DMA-stream overflow frames during the 302,460-cycle VBlank.
- Enforce hardware limits in the IDE as static checks with clear messages: 128 sprites per screen, 32 affine (rotated/scaled) sprites per screen, ~1,200 sprite pixels on any one scanline, 1024 tiles per text layer, 512x512 px native map size (larger rooms use ring-buffer scrolling), 16 sound channels, room asset budget vs the arena size.
- Phase the renderer: Phase 1 uses OAM sprites on both screens (simple and predictable); Phase 2 optionally renders main-screen sprites as textured quads on the 3D engine (2,048 polygons/frame, 512 KB textures) to get free rotation, scaling, alpha and tint on unlimited sprites, the way MicroLua did.
- Keep the bytecode format and native-builtin ABI versioned and documented from day one so a later 'export as native' transpile backend (Strategy C) can be added without touching the VM or the IDE; measured GCC compile latency for a mid-size project is only 1-3 s, so this is feasible but optional.
- Pack all assets pre-converted into NitroFS (tiles/maps/palettes/collision masks, maxmod soundbank via mmInitDefault("nitro:/soundbank.bin")), read whole files with large fread calls and DC_FlushRange before DMA; assume ~1 MB/s worst-case DLDI reads on flashcarts and near-instant reads on emulators. Require loaders that pass argv[0] (Homebrew Menu / TWiLight Menu) in the user docs.

## Open questions
- Exact DS per-scanline OBJ render budget: GBATEK documents the GBA rule (1210 cycles, n per normal sprite pixel, 10+2n affine) but I could not locate the DS-specific figure; validate on hardware/melonDS before setting the IDE's 'sprites per scanline' warning threshold.
- Real-world NitroFS throughput on flashcarts (DLDI) and DSi SD: no published KB/s table was reachable (GBAtemp 403). Run ApacheThunder's dldi-driver-benchmark on the user's actual cart, or budget conservatively at ~1 MB/s until measured.
- Hardware divider/sqrt latencies (GBATEK 'DS Maths' lists 18/34 cycles for div and 13 for sqrt from memory) were not re-verified in this pass; confirm before deciding whether divf32 stays a builtin or is inlined into the VM.
- Whether to build the runtime with BlocksDS (Wonderful toolchain, GPL/zlib libs, DSi-aware, active) or classic devkitARM; BlocksDS installation on Windows through its wf-pacman/MSYS2 flow should be verified by the toolchain subagent since the user already has MSYS2 at C:\msys64.
- Emulator choice for the Play button: DeSmuME 0.9.13 is already present and scriptable from the command line, but melonDS is more timing-accurate (cart transfer delays, ARM9 cache effects) and would give truer performance previews; consider supporting both via a configurable launcher.
- DMA bandwidth main RAM -> VRAM during VBlank was not measured; the plan assumes tens of KB per VBlank for streamed sprite frames and should be verified with a microbenchmark in the runtime's first milestone.
- Whether GML-style per-pixel ('precise') collision is worth supporting on 67 MHz; the recommendation is AABB/circle by default with masks opt-in, but the acceptable instance count with masks enabled needs a benchmark once the collision module exists.
- Value-cell width trade-off (8-byte tagged cells everywhere vs 4-byte untagged reals for type-proven instance slots) should be decided by the compiler subagent based on how much static typing the language spec commits to.
