# Prior art for a GameMaker-style Nintendo DS IDE, and a GML-like language subset for it

## 1. DS Game Maker (DSGM) — the direct ancestor

**History and fate.** Written in Visual Basic .NET 2008 by James Garner (15–16 years old at the time, West Yorkshire); first release 26 May 2008 per the v5 manual, active roughly 2007–2012, site/forum offline in 2016 and mostly *not* archived. Free edition: 10-object limit, 5-room limit, splash screen; Pro was $14.99 lifetime. In Aug 2009 it had 62 Pro sales vs 6,000+ downloads and 111 built-in actions vs ~1,000 in Game Maker (gamemakerblog.com, 2009). Final official build 5.20 (free, all Pro features); source recovered and 5.21 shipped in 2022 by DigitalDesignDude; a 2020 VirtualBox .ova bundles DSGM 4.9/5.12 with devkitPro 1.50 + PAlib because "ALL former releases are now 100% obsolete" on modern Windows (dsgamemaker.online). Sources: https://digitaldesigndude.github.io/DSGM-Resource-Site/about.html , https://archive.org/details/dsgamemakerbundle , https://gamemakerblog.com/2009/10/05/dsgamemaker-can-we-learn-anything-about-game-maker/ , manual PDF at https://digitaldesigndude.github.io/DSGM-Resource-Site/hosted-files/DS%20Game%20Maker%205%20Manual.pdf .

**Why it died (synthesised):** (1) built on PAlib, which was retired in 2008 and dropped by devkitPro, so the toolchain froze at devkitPro 1.50/Win7; (2) VB.NET/.NET 3.5 desktop app, Windows-only, buggy 5.20 installer; (3) a solo teenage author who moved on; (4) "documentation is the biggest flaw" (2009 review) — community YouTube tutorials replaced a manual; (5) the planned remake on CTurt's dsgmLib (an OO-in-C engine, `void ball_touch(ballObjectInstance *me)`, with the warning that all instance pointers are invalid after `DSGM_CreateObjectInstance`/`DSGM_DeleteObjectInstance`) never shipped as an IDE (https://cturt.github.io/dsgmLib.html , https://github.com/CTurt/dsgmLib).

**Project model (from the v5 manual).** Resources: Sprites, Objects, Backgrounds, Sounds, Rooms, Paths, Scripts. Explicitly "the same events and actions system as Game Maker": each Object has a list of Events; each Event has an ordered list of Actions. Events seen: Create, Step ("every frame, most useful on the controller object"), Collision with <Object>, Button Press (L/R/A/B/Start…), Touch (New Press / Held / Released), plus alarms via `Set_Alarm(AlarmID, Time)`. Nesting was done with literal "Start Block"/"End Block" actions and an "If Object Instances" action — the clunkiest part of the UX. Actions were C templates with typed arguments (`Screen`, `TrueFalse`, `Variable`, `Object`, `Sprite`, `Room`, `Sound`, `Comparative`, `Font`…) substituted as `!1!`, `!2!` in an Action Editor. Rooms hold **two backgrounds, one per screen**; the room editor shows both DS screens; rooms can be larger than 256×192 (e.g. 768×192) and a "Views" camera scrolls (`Set_Camera_XY(Screen, X, Y)`).

**Runtime model.** Generated C + PAlib: `Instances[0..127]` is a fixed struct array `{s16 OriginalX, OriginalY, X, Y; bool Screen, InUse; u8 Width, Height, ObjectID; u16 Frame; bool FrameChanged; u8 SpriteID}` — the instance ID *is* the PAlib sprite slot, so **128 instances per room total across both screens**, synced to OAM in VBL by `DSGM_ObjectsSync()`. Collision: `IsSpriteCollision(screen, a, b)` (midpoint-based, same screen only) and `IsBgCollision(screen, x, y, layer)` (magenta-pixel test). Variables: Global (Tools > Global Variables manager, predefined `score`, `lives`, `health`) or "Eventual" (`s16` or `bool`, scoped to one event). Property placeholders `[X] [Y] [VX] [VY] [Frame] [Screen] [OX] [OY] [Width] [Height] [Me]` replaced GM's "Relative" checkbox. Function API (coding reference): `Create_Object(ObjectName, InstanceID, Screen, X, Y)` with `NextInstance()`, `Get_Single_ID(Obj)`, `Count_Instances`, `Delete_Instance`, `Set_XY`, `Animate(ID, First, Last, FPS)`, `Set_Sprite`, `Object_Under_Point(Screen, X, Y, Obj)`, `Draw_Text(Screen, XTiles, YTiles, Text)`, `Draw_Score/Lives/Health`, `Set_BG_Scroll`, `Random(min,max)`, `Test_Chance(n)`, `Goto_Next_Room()`, `Stream_BG_Sound`, and Pro-only `Set_Angle`, `Angle_Between_Points`, `Distance_Between_Points`, file I/O. Input was PAlib's raw `Pad.Newpress.A`, `Stylus.Newpress`, `Stylus.X/Y`. Build: PAGfx converts graphics, then devkitARM `make` on generated `source\main.c`; F5 tested in NO$GBA; "Open Compile Temp" exposed `build.bat`/`clean.bat`. https://digitaldesigndude.github.io/DSGM-Resource-Site/dsgm-coding-ref.html

**DBAS** ("Dynamic BASic", "Coding at a Glance" PDF): `'` comments; `Dim x As Integer = 5` / `Public g As Boolean`; types Integer (16-bit default), String, Boolean, Signed/Unsigned Byte, Float ("take up lots of memory"); `If X = 5 … End If` (single `=`, "never a need for 2 equal signs"); `For i = 0 To 10 … Next`; no `While`. C and DBAS could be mixed in one script — a documented source of syntax errors.

## 2. GB Studio — the model to copy for architecture

**Stack.** UI in JS/TypeScript (React + Electron), engine in C compiled with GBDK (SDCC); visual events compile to "GBStudio Assembly" (.s files of SDAS macros emitting bytecode) and link into the engine ROM. https://www.gbstudio.dev/about/ , https://gbstudiocentral.com/tips/understanding-gbvm/

**Project model.** Scenes have a *Type* (Top Down 2D, Platformer, Adventure, Shoot 'Em Up, Point and Click, Logo; plugins add more), a background, and scripts *On Init* / *On Player Hit*. Actors: sprite sheet, movement speed, animation speed, collision group, pin-to-screen, Is Solid / Is Platform; scripts *On Init, On Interact, On Hit, On Update* ("repeatedly called while on screen; once the script finishes it repeats"). Triggers: *On Enter / On Leave*. Hard limits are shown live in the status bar `A: 0/20  S: 0/96  T: 0/30`: 20 actors, 30 triggers, 64–96 sprite tiles (mono) or 128–192 (Color Only), and a warning if >10 actors share one 160×144 screen. Sprite types fix the animation slots (Static, Animated, Actor = 3 directions with auto-flipped left, Animated Actor, Platformer Player with jump/climb) and named Animation States switched with "Set Actor Animation State". https://www.gbstudio.dev/docs/project-editor/scenes/limits/ , https://www.gbstudio.dev/docs/assets/sprites/

**GBVM (verified from source, https://github.com/chrismaltby/gbvm `include/vm.h`, `src/core/vm.c`, `src/core/vm_instructions.c`).**
- Harvard model: bytecode in ROM banks, VM RAM = `UWORD script_memory[VM_HEAP_SIZE + VM_MAX_CONTEXTS*VM_CONTEXT_STACK_SIZE]` with `VM_HEAP_SIZE 768`, `VM_MAX_CONTEXTS 16`, `VM_CONTEXT_STACK_SIZE 64` → 3,584 bytes total. All variables are INT16 (−32768..32767). Positive indices = global heap, negative = relative to the context's stack pointer (`VM_REF_TO_PTR`), so locals and args (`.ARG0` = −1) cost nothing extra.
- `SCRIPT_CTX {PC, bank, next, update_fn, stack_ptr, base_addr, ID, hthread, terminated, waitable, lock_count, flags}`; opcode table `SCRIPT_CMD {fn, fn_bank, args_len}` — 149 rows, ~133 populated; `args_len` lets `VM_STEP` (hand-written asm) advance PC without each handler knowing its size.
- Scheduler `script_runner_update()`: round-robin over a linked list of contexts; each gets `INSTRUCTIONS_PER_QUANT = 0x10` instructions per call or until it sets `waitable` (via `vm_idle`, waits, loops); `VM_LOCK` pins the scheduler to one thread; returns RUNNER_DONE / IDLE / BUSY. `script_execute(bank, pc, handle, nargs, …)` pushes args as thread-locals; `VM_BEGINTHREAD`, `VM_JOIN`, `VM_TERMINATE` manage threads by ID.
- Expressions: one `VM_RPN` opcode with a byte-coded postfix stream (27 ops: EQ LT LE GT GE NE AND OR NOT ADD SUB MUL DIV MOD B_AND B_OR B_XOR SHL SHR MIN MAX ATAN2 ABS B_NOT NEG ISQRT RND, plus I8/U8/I16 memory refs) — the whole "language" is ~30 primitive operators plus ~130 engine calls (actor, camera, overlay/text, music, input, scene stack, fade, timers, save).
- Engine access is via C variables exposed as **Engine Fields** (`engine.json`), editable in Settings and from scripts ("Engine Field Update"). **Engine Eject** copies the C engine into `assets/engine/{include,src/core,...}`; missing files fall back to the built-in engine.

**Plugins.** Four kinds: asset, script-event (JS: `{id, name, groups, fields, compile(input, helpers)}` with helpers like `_stackPushConst`, `_callNative`, `_declareLocal`, `variableSetToScriptValue`, `actorDeactivate`, `soundPlay`, `textDialogue`, `getNextLabel/_label/_jump`), engine (override single C files), scene-type (C `init()/update()` + JSON). https://www.gbstudio.dev/docs/extending-gbstudio/plugins/ , https://www.morphoice.com/gameboy/event-plugins

**Beginner UX decisions worth copying:** one Play button that builds and opens an emulator window; "Run From Here" on any scene; export to `build/rom/game.gb`, web (480×432 iframe) or `.pocket`; a Sample Project template; hard limits surfaced as meters, not compile errors; a small fixed set of script hooks per entity; a global list of named animation states.

## 3. NESmaker — the cautionary tale

Sells "no code" NES creation via 7–8 assembly *modules* (Adventure, Arcade, Platformer, Brawler, Horizontal Shooter, LR Platformer, Maze, MetroVania) on mapper 30; object AI is a table of *Action Steps 0–7* with reactions (Solid/Edge Object Reaction: Reverse Direction / NULL / Destroy Me) and timers. NESdev reviewers: "Nothing is intuitive", single-screen level editing, keyboard-shortcut-only functions, a "disgusting" graphics editor, buggy modules, minimal docs, no demo, and the "no coding" claim collapses the moment anything custom is needed (a 30-year veteran quit after 30 hours). https://forums.nesdev.org/viewtopic.php?t=17656 , https://board-b.com/tutorials/written-tutorials/nesmaker-tutorials-unofficial/modules/

## 4. Butano (GBA) and Nitro Engine / NFlib (DS)

**Butano**: "one line of C++" sprite creation; RAII handles (`bn::sprite_ptr`, `bn::regular_bg_ptr`) modelled on `shared_ptr` so hardware slots free themselves; no heap, no exceptions; fixed 60 FPS `bn::core::update()`; assets are PNG + a sidecar `.json` in `graphics/` run through grit at build time; limits stated bluntly in the FAQ (128 sprites, 4 regular or 2 affine BGs, 256 colours per side, 32 KB IWRAM / 256 KB EWRAM); `bn::to_string` is >5× faster than `sprintf`; 20+ released games. https://gvaliente.github.io/butano/faq.html , https://github.com/GValiente/butano

**Nitro Engine** (SkyLyrac/AntonioND): 3D + "2D via 3D hardware", dual-screen 3D at 30 FPS, OBJ/MD5 (DSMA) models, libDSF text, AABB physics, `NE_` prefix; **BlocksDS only** (`wf-pacman -Sy blocksds-nitroengine`; devkitPro support "temporarily removed"); melonDS recommended for 3D accuracy. https://github.com/AntonioND/nitro-engine

**NFlib** (`blocksds-nflib`): 256-colour tiled BGs (32 in RAM, extended palettes), 128 hardware sprites per screen, 3D-sprites up to 256 on screen, collision maps, MIT. https://github.com/knightfox75/nds_nflib

## 5. Scripting VMs on DS

- **MicroLua DS** (v4.7.2, 2014-01-04, Lua 5.2.2; BlocksDS port by asiekierka): draws 2D through the 3D GPU via µLibrary (wiki: 30 FPS per screen in dual-screen mode). API shape: `screen.blit(scr, x, y, img)`, `Image.load(path, RAM|VRAM)`, `Sprite.new(graph, frameW, frameH, dest)`, `sprite:addAnimation({frames}, delay)`, `Map.new/ScrollMap.new(img, mapfile, w, h, tileW, tileH)`, retained-mode `Canvas` objects, `Keys.newPress.A`, `Stylus.X/Y/held/doubleClick`, `Timer.new()`, Maxmod `Sound.loadBank/startMod/startSFX`, Wifi, INI, constants `SCREEN_UP/SCREEN_DOWN`, `SCREEN_WIDTH`. No published FPS/benchmark numbers exist. https://sourceforge.net/p/microlua/wiki/API471/ , https://github.com/asiekierka/micro-lua-ds
- **DSLua** (2006–07, v0.7, PAlib-based): sprites/backgrounds/tilemaps/sound; crash-prone ("lock up instead of printing an error"). https://www.gamebrew.org/wiki/DSLua
- **NDSPython / dspython**: Stackless Python 2.5; console only, no hardware access; the Develer fork wrapped libnds with Pyrex but was "completely unreliable on hardware… corrupts at random". https://www.gamebrew.org/wiki/NDSPython , https://github.com/develer-staff/dspython
- **ndsChaury** (2020s): experimental C++ + embedded Lua with `awake()/start()/renderTop()/renderBottom()`, .pcx assets compiled in; author notes dual-screen buffer/swap overhead. https://github.com/BacioiuC/ndsChaury
- Takeaway: general-purpose interpreters *run* on the 67 MHz ARM946E-S (no FPU, 4 MB RAM) but every DS scripting project either had no perf data, was crash-prone, or exposed raw hardware slots. A purpose-built INT/fixed-point bytecode VM (GB Studio style) is the proven path.

## 6. PAlib naming as a beginner API example

532 `PA_*` identifiers (Doxygen ref, 2010). Convention: **screen first, hardware slot second**: `PA_CreateSprite(u8 screen, u8 obj_number, void* obj_data, u8 obj_shape, u8 obj_size, u8 color_mode, u8 palette, s16 x, s16 y)`, `PA_SetSpriteXY(screen, sprite, x, y)`, `PA_StartSpriteAnim(screen, sprite, first, last, speed)`, `PA_LoadSpritePal(screen, palnum, pal)`, `PA_EasyBgLoad(screen, bg, name)`, `PA_EasyBgScrollXY(screen, bg, x, y)`, `PA_SetMapTile(screen, bg, x, y, tile)`, `PA_OutputText(screen, x, y, fmt, ...)`, `PA_SetRotset(screen, rotset, angle, zoomx, zoomy)`, `PA_SpriteTouched(sprite)`, `PA_StylusInZone(x1,y1,x2,y2)`, `PA_Distance`, `PA_RandMinMax`, `PA_WaitForVBL`, `PA_PlaySimpleSound`, input structs `Pad.Newpress/Held/Released.A`, `Stylus.Newpress/Held/Released/X/Y/Vx/Vy`. Good: verbs are obvious, "Easy" helpers hide VRAM. Bad: users hand-manage OBJ numbers 0–127, palette numbers, rotsets 0–31 and screens — exactly the bookkeeping DSGM inherited. PAlib was retired in 2008, kept alive only as legacy `blocksds-palib` ("better alternatives exist"). https://www.gamebrew.org/wiki/PA_lib , https://blocksds.skylyrac.net/docs/libs/additional_libs/

## 7. GML essentials beginners actually use (verified against manual.gamemaker.io)

- **Events**: Create, Destroy, Clean Up, Begin/Step/End Step, Alarm 0–11, Draw (Pre/Begin/Draw/End/Post/GUI), Keyboard / Key Press / Key Release, Mouse (local/global press/release, enter/leave), Collision <obj>, Other (Outside Room, Intersect Boundary, Room Start/End, Game Start/End, Animation End, Animation Update, Path Ended, User 0–15, Broadcast), Async, Gesture. **Frame order**: Begin Step → timelines/time sources → Alarms → Step → built-in movement (hspeed/vspeed applied) → collisions (solid revert) → End Step → Draw events. Instance order within an event is not guaranteed.
- **Built-in instance vars**: id, object_index, x, y, xprevious, yprevious, xstart, ystart, speed, direction (0°=right, 90°=up), hspeed, vspeed, gravity, gravity_direction, friction, sprite_index, sprite_width/height, sprite_xoffset/yoffset, image_index, image_number, image_speed, image_xscale/yscale, image_angle, image_alpha, image_blend, mask_index, bbox_left/right/top/bottom, visible, solid, persistent, depth, layer, alarm[].
- **Semantics**: real (double), string, bool (>0.5 is true), undefined, array (0-based, grows on assignment, by reference), struct, method, handle, int64, NaN/infinity. `var` locals die at end of event; instance vars exist on first assignment; `global.x`; `globalvar` deprecated; `obj.var` reads the *first* instance and writes *all*; `self`(−1)/`other`(−2)/`all`(−3)/`noone`(−4) "never use the numbers"; `with(target){}` iterates instances, `other` = caller inside. Operators: `= += -= *= /= ++ --`, `== != < > <= >=` (`=` in comparisons is legacy), `&& || ^^ !`, `div mod %`, `?:`, `??`, string `+` requires both strings. Statements: if/else, switch, repeat, while, do/until, for, break, continue, exit, return, with, `function name(a, b = 90) {}`, `argument_count`. Core functions: instance_create_layer/depth, instance_destroy, instance_exists, instance_find, instance_number, instance_nearest, instance_place, instance_position, place_meeting/place_free/position_meeting, collision_point/rectangle/circle/line, motion_add/motion_set, move_towards_point, move_bounce/contact/outside_solid, move_wrap, keyboard_check(_pressed/_released) + vk_*, draw_sprite_ext(sprite, subimg, x, y, xscale, yscale, rot, colour, alpha), draw_text, draw_set_color, draw_rectangle, room_goto/_next/_previous, room_restart, game_restart, audio_play_sound(snd, priority, loop), audio_stop_sound/all, audio_is_playing, random/random_range/irandom/irandom_range/choose/randomize, floor/ceil/round/abs/sign/frac/sqrt/power, min/max/clamp/lerp, point_distance/point_direction/lengthdir_x/y, string()/real()/string_length, array_length/array_push, show_debug_message.

## 8. Lessons learned

1. **Objects + events + instances is the right mental model** — DSGM ("the same events and actions system as Game Maker") proved DS beginners get it; its failures were tooling, not the model.
2. **Never bind instance count to a hardware slot.** DSGM's `Instances[128]` == OAM slot capped a room at 128 instances *across both screens* and made every collision "same screen only". Keep a logical instance list, allocate OAM per screen per frame (Butano's `sprite_ptr` shows the handle pattern).
3. **Separate engine from game data (GB Studio).** A prebuilt C runtime + compiled bytecode/assets means Play never needs a C compiler on the user's PC; DSGM regenerated and recompiled `main.c` every F5 and died with its toolchain.
4. **Tiny integer VM beats a general interpreter on this class of CPU.** GBVM runs 16 threads in 3.5 KB with INT16 vars, 16-instruction quanta, one RPN opcode for all maths. Lua/Python on DS never produced perf numbers and were crash-prone.
5. **Give scripts real syntax, not "Start Block/End Block" actions.** DSGM's block actions and DBAS's `If X = 5` single-`=` semantics were the top confusion sources; GML's `==` with a lint for `=` is better.
6. **Surface hardware limits as live meters** (GB Studio `A: 0/20 S: 0/96 T: 0/30`; Butano FAQ tables), never as link-time errors.
7. **Fix the screen model early**: DSGM made `Screen` a per-instance property and gave rooms two backgrounds — that worked. Add a per-screen camera/view.
8. **Ship templates and a sample game, not empty "modules"** — NESmaker's modules locked users in; DSGM deliberately avoided "driving game" templates but shipped example projects.
9. **Documentation is a feature**; both DSGM and NESmaker were reviewed as undocumented. Generate the API reference from the same table the compiler uses.
10. **Make the engine extensible without forking it** (Engine Fields, ejectable engine, JS event plugins) — that is how GB Studio's community outgrew the built-ins.
11. **Bundle the emulator in the Play button** (DSGM used NO$GBA; GB Studio opens a window). melonDS offers a GDB stub (Config > Emu settings > Devtools, port 3333, disable JIT); DeSmuME 0.9.13 takes the ROM as a positional argument and `--arm9gdb PORT` only if built with GDB_STUB.
12. **Pick a living toolchain.** BlocksDS is where Nitro Engine, NFlib, µLibrary, MicroLua and even PAlib now live (Windows: install Wonderful Toolchain, then `wf-pacman -Syu wf-tools`, `wf-config repo enable blocksds`, `wf-pacman -Syu`, `wf-pacman -S blocksds-toolchain`, build from the "Wonderful Toolchain Shell"). The mwccarm bundle has no NitroSDK headers/libs, so it cannot build a DS runtime without hand-written hardware code.

## 9. Recommended minimal-but-complete language and API (v1)

**Language ("GML-like", C-style).** Comments `//` and `/* */`; statements if/else, while, for, repeat(n), do…until, switch/case/default, break, continue, return, exit; `var` locals; instance vars on first assignment; `global.name`; `function name(a, b = 1) {}` in Scripts; `with (target) {}` with `self/other/all/noone`; arrays `[]`, 0-based, nested for 2D; operators `+ - * / div mod % ++ -- += -= *= /= == != < <= > >= && || ! ?:`, string `+`; `#macro`. **Types**: number, string, bool, undefined, array, instance-id, asset-id. **Numbers**: Lua-5.3-style dual subtype — int32 for counters/scores, Q16.16 fixed-point "real" for positions/speeds (auto-promote on fractional results); no doubles because the ARM9 has no FPU. Comparisons with `=` inside `if` compile as `==` with a warning (DBAS/legacy-GML habit).

**Object model.** Objects with events: Create, Destroy, Step (Begin/Step/End), Alarm 0–7, Draw (optional; default draw_self), Collision <object> (bbox only), Button (per DS button; Press/Release/Held), Touch Press/Release/Held, Room Start/End, Animation End, Outside Room, User 0–7. Built-ins: id, object_index, x, y, xprevious, yprevious, xstart, ystart, speed, direction, hspeed, vspeed, gravity, gravity_direction, friction, sprite_index, image_index, image_number, image_speed, image_xscale, image_yscale (affine, max 32 per screen, 1–2× hardware range), image_angle (affine only), visible, depth (maps to OAM order + priority 0–3), alarm[0..7], bbox_*, **screen** (SCREEN_TOP / SCREEN_BOTTOM), sprite_width/height. Rooms: width/height ≥ 256×192, background per screen (tiled, ≤1024 tiles, 16×16-colour or 256-colour palettes), view_x/view_y per screen, room_speed fixed 60.

**API surface (≈90 calls).** Instances: instance_create(x, y, obj) (+ accept instance_create_layer/_depth aliases), instance_destroy, instance_exists, instance_number, instance_find, instance_nearest, instance_place, instance_position, place_meeting, position_meeting, place_free, collision_rectangle/point. Movement: motion_add, motion_set, move_towards_point, move_wrap, point_distance, point_direction, lengthdir_x/y, distance_to_object. Input: button_check/_pressed/_released(btn_a … btn_start, btn_lid), keyboard_check aliases mapping vk_left → btn_left, touch_check/_pressed/_released, touch_x, touch_y, touch_dx/dy, touch_in_instance(id). Drawing (Draw event only): draw_sprite, draw_sprite_ext, draw_self, draw_text (fixed 8×8 font on a text layer), draw_set_color (palette-indexed), draw_set_screen, draw_rectangle (bitmap/3D-quad layer, optional), draw_clear. Rooms/game: room_goto, room_goto_next/previous, room_restart, game_restart, game_end. Audio (Maxmod): audio_play_sound(sfx), audio_stop_sound, audio_play_music(mod, loop), audio_stop_music, audio_set_volume. Math: floor, ceil, round, abs, sign, frac, sqrt, min, max, clamp, lerp, random, random_range, irandom, irandom_range, choose, randomize, sin/cos via lookup tables (dsin/dcos degrees). Strings: string, real, string_length, string_char_at, string_upper/lower, string_repeat, chr/ord. Arrays: array_length, array_push, array_pop, array_create, array_delete. Debug: show_debug_message (nocashMessage → melonDS/NO$GBA console), assert.

**DS additions**: `screen` per instance and per draw; two backgrounds per room; `view_x[screen]`; touch API; lid event; hard limits surfaced in editor: 128 sprites/screen, sprite sizes 8×8…64×64 (12 shapes), 32 affine sets/screen, 4 BG layers/screen, 16 palettes × 16 colours (or 256/ext), ≤1024 tiles per regular BG, alarms 8, instances 256 (logical).

**Deliberately omit in v1**: structs/constructors/methods/`new`, try/catch/throw, enums, `ds_list/ds_map/ds_grid` (use arrays), physics, paths/timelines/sequences, layers API, cameras beyond one view per screen, surfaces/shaders/particles, `image_blend`/`image_alpha` (DS has only coarse per-layer blending), precise (pixel) collision and `solid`/move_outside_solid, `persistent` instances/rooms, gamepad/mouse APIs (button/touch replace them), keyboard_string/text input, async/networking/files (save slots later), 3D, draw_text_ext/custom fonts, floating-point doubles and int64.

## Recommendations
- Adopt GB Studio's architecture, not DSGM's: build ONE C runtime ROM once (BlocksDS + libnds + Maxmod), and have the IDE's Play button only compile scripts to bytecode and pack bytecode + converted assets into NitroFS. No per-run C compile, so the user never needs the toolchain after the runtime is built.
- Install BlocksDS for the runtime (Wonderful Toolchain installer, then `wf-pacman -Syu wf-tools`, `wf-config repo enable blocksds`, `wf-pacman -Syu`, `wf-pacman -S blocksds-toolchain`, build inside the Wonderful Toolchain Shell). Do not plan on mwccarm: the bundle has no NitroSDK headers/libs, so it cannot target DS hardware without register-level code.
- Design the VM as a small stack machine with a single RPN 'expression' opcode (GBVM style), cooperative script threads with an instruction quantum (GBVM uses 16), and value type = int32 | Q16.16 fixed (Lua-5.3-style promotion). Avoid doubles entirely (ARM946E-S has no FPU).
- Keep a logical instance list decoupled from OAM: allocate OAM entries per screen each frame and treat 128 sprites per screen, 32 affine sets per screen, and 4 BG layers per screen as budgets the editor displays live (like GB Studio's `A: 0/20 S: 0/96 T: 0/30`).
- Fix the dual-screen model in the data format from day one: each room has a background per screen; each instance has a `screen` built-in; draw functions accept/inherit the current screen; touch input only exists on the bottom screen.
- Give the language real C-like syntax (blocks, ==, var, with) rather than action blocks; accept `=` inside conditions as comparison with a lint warning to catch the DBAS/legacy-GML habit.
- Ship a curated API of about 90 functions and a fixed event set (Create, Destroy, Step, Alarm 0-7, Draw, Collision, Button, Touch, Room Start/End, Animation End, Outside Room); generate the reference docs and editor autocomplete from the same function table the compiler uses so documentation cannot drift.
- Provide extension seams early: an 'engine fields' JSON that exposes C runtime tunables to the IDE, and a native-function table so advanced users can add C functions callable from scripts without forking the IDE (GB Studio's Engine Fields / eject pattern).
- Bundle melonDS (preferred: GDB stub on port 3333, accurate 3D, `melonDS.exe rom.nds`) or the already-downloaded DeSmuME 0.9.13 (`DeSmuME_0.9.13_x64.exe <rom.nds>`) behind the Play button; route show_debug_message to nocashMessage so it appears in the emulator console.
- Ship a sample project and 2-3 templates (top-down, platformer, touch/minigame) with the IDE instead of empty NESmaker-style modules, and include an asset pipeline that converts PNG to tiles/palettes automatically (grit) with clear errors for palette overflow.
- Split the build into parallel workstreams that only meet at two contracts: (1) the bytecode format + native function table spec, and (2) the NitroFS asset pack format. Then the language/compiler, the C runtime, the asset converter, the editor UI, and the emulator/build integration can be developed by separate Claude Code instances.
- Defer structs, data structures, physics, paths, precise collision, persistent instances, custom fonts, files/saves, networking and 3D to later versions; document the omission list in the manual so beginners porting GML knowledge know what to expect.

## Verified facts
- [high] DS Game Maker used Game Maker's events-and-actions model: each Object has Events (Create, Step, Collision with <Object>, Button Press, Touch New Press/Held/Released) and each Event an ordered list of Actions; nesting used explicit 'Start Block'/'End Block' actions. (source: DS Game Maker 5 Manual PDF (digitaldesigndude.github.io/DSGM-Resource-Site/hosted-files/DS%20Game%20Maker%205%20Manual.pdf), sections 'Getting to Grips', 'Working with an Object', 'Blocks of Logic')
- [high] DSGM's runtime used a fixed Instances[0..127] struct array where the instance ID is the PAlib sprite slot; a room can hold 128 instances (IDs 0-127) across both screens; IsSpriteCollision only works when both instances are on the same screen. (source: DS Game Maker 5 Manual, sections 'Instancing', 'The Internals of DSGM', 'IsSpriteCollision')
- [high] DSGM Free edition limited projects to 10 objects and 5 rooms plus a splash screen; Pro cost $14.99 lifetime. In Aug 2009: 62 Pro copies sold vs 6,000+ downloads; 111 built-in actions vs ~1,000 in Game Maker; written in VB.NET 2008. (source: DSGM 5 Manual 'Pro Edition'; gamemakerblog.com/2009/10/05/dsgamemaker-can-we-learn-anything-about-game-maker/)
- [high] DSGM was developed ~2007-2012 by James Garner, site and forum offline in 2016 (forum mostly unarchived), final official version 5.20 free; 2020 VirtualBox .ova bundles DSGM 4.9/5.12 with devkitPro 1.50 + PAlib; source recovered and 5.21 released 2022 by DigitalDesignDude. ## Open questions
- No published performance numbers exist for any Lua/Python interpreter on real DS hardware (MicroLua, DSLua, ndsChaury); if a Lua-based approach is ever reconsidered, a benchmark of Lua 5.4 with LUA_32BITS on a 67 MHz ARM9 (via melonDS with accurate timing or real hardware) would be needed.
- GB Studio's actor limit differs between the stable docs (20 per scene) and the develop docs (30); the underlying constraint is sprite tile memory, so the exact per-scene limits for a DS runtime must be derived from OAM/VRAM budgets rather than copied.
- Whether the DeSmuME 0.9.13 Windows binary already on this machine was compiled with GDB_STUB is unknown (the --arm9gdb option only exists when it is); melonDS is the safer choice for a debug-capable Play button and would need to be downloaded.
- BlocksDS docs do not mention MSYS2 compatibility; it is unclear whether the Wonderful Toolchain shell and the user's existing MSYS2 UCRT64 setup can share a make/PATH without conflicts, or whether the IDE should invoke the Wonderful shell scripts directly.
- The DSGM 5 manual lists 'Alarm' only through the Set_Alarm function and the event dialog description was image-only in the PDF, so the exact list of DSGM event types (e.g., whether Alarm and Animation End existed as events) is not fully confirmed.
- How dsgmLib (the intended DSGM 6 engine) allocated OAM per screen and whether it lifted the 128-instance cap could not be verified beyond its README's pointer-invalidation warning; the repository source would need to be read directly.
- The numeric representation choice (int32 + Q16.16 promotion vs a single Q20.12 fixed type) trades score/counter range against fractional precision; a prototype VM benchmark should decide it before the language spec is frozen.
- GB Studio's exact bundled GBDK-2020/SDCC version and its build-folder layout were not confirmed from the docs pages fetched; only 'GBDK' is stated on the About page.
