# Design panel summary (2026-09-24)

Four architects wrote independent plans from different lenses; three judges scored them (1-10 per criterion, 50 max). The unified plan in `PLAN.md` was synthesised from the winner with ideas grafted from the others.

| Plan (lens) | Judge 1 | Judge 2 | Judge 3 | Total |
|---|---|---|---|---|
| 0: pipeline-first | 41 | 39 | 40 | **120** |
| 1: beginner-ux-first | 38 | 40 | 37 | **115** |
| 2: language-first | 36 | 36 | 38 | **110** |
| 3: parallel-first | 39 | 37 | 37 | **113** |

Winner: plan 0 (pipeline-first). Judges endorsed grafting: the runtime core/platform split and host-side oracle (language-first plan), the ownership hook / ADR / phase0-tag mechanics (parallel-first plan), and the beginner journey table and acceptance gate (beginner-ux-first plan).

## Decisions the judges converged on

- Toolchain: all four choose BlocksDS 1.24 via the Wonderful bootstrap into C:\msys64 and reject mwccarm (no headers/libc/crt0/ARM7, proprietary, 32-bit, non-redistributable) and dsd (retail-ROM relinker). Endorse unanimously; the mwccarm folder's only legitimate use is offline code-size inspection (Plan 2) and it must stay gitignored. Only Plan 3 names a plan B (devkitPro pacman, auto-install only, never redistributed); adopt that fallback since the silent Inno install into an existing MSYS2 is unverified on this machine.
- VM vs transpile-to-C: all four pick a bytecode VM inside a prebuilt runtime ELF with ndstool repacking on Play. Endorse: end users never install a compiler, Play is sub-second, runtime faults carry file:line instead of an ARM exception. Keep native export as a post-v1 backend behind the versioned bytecode/ABI hash. Caveat for all four: the 19-27 cycles/op numbers are estimates until a cycle-counted benchmark runs on melonDS (Plan 2's M1 microbenchmark); make that a hard gate before the engine grows.
- Runtime testability: Plans 0, 2 and 3 build the C VM/engine on the host with MSYS2 UCRT64 gcc (verified present, with gdb-multiarch and mingw32-make); Plan 1 tests the C runtime only through emulator runs plus a TS reference VM for the compiler. Endorse host builds, specifically Plan 2's dsd_platform.h seam and headless trace runner; a TS mini-interpreter is a useful addition for compiler goldens but not a substitute.
- Runtime workstream split: Plans 0, 1 and 3 keep one runtime stream (Plan 0 splits VM/engine only after M2); Plan 2 splits core (host-testable) from DS platform layer from day 1 with a selftest ROM. Endorse Plan 2's split: the runtime is the 4-6 week critical path and the platform seam is the only way two instances work on it without stepping on each other.
- Asset conversion: Plans 0 and 3 quantize in-house then call grit (-ftr GRF) and mmutil; Plan 2 writes GRF in-house; Plan 1 invents custom .spr/.bgt/.tls formats with TS encoders and decoders. Endorse Plan 0 for v1: in-house RGB555 quantization (grit's own quantizer is poor) feeding grit behind a ToolPaths wrapper, because grfLoadPath is proven and BG tile/flip dedup comes free; note Plan 0's -mRtf is correct for 8bpp text BGs whereas Plan 3's -mRtpf is not. An in-house GRF writer (Plan 2) is a reasonable v1.1 swap if bundling grit and its DLLs proves painful; custom formats (Plan 1) add loader work on both sides for no gain.
- Emulator: all default to melonDS 1.1 (no BIOS, GDB stub, 0x04FFFA18 forwarded to stdout, generated melonDS.toml because it ships without key bindings) with DeSmuME 0.9.13 as fallback and dual nocash output. Endorse. They differ on log capture: Plans 0 and 1 make node-pty primary; Plans 2 and 3 use batched pipes plus an on-screen console and defer node-pty. Endorse Plans 2/3: vswhere.exe is present so node-gyp may work, but a native module in the Electron build worker is an avoidable v1 dependency; batched logs are acceptable for M4 and DeSmuME flushes nocash prints immediately anyway.
- IDE stack: unanimous Electron 44 + electron-vite 5/Vite 7 + React 19 + Monaco 0.57 + PixiJS 8 + dockview + zod IPC + TypeScript throughout (no Rust/CMake on the machine, Node 24 present). Endorse; Plan 1's Tailwind/radix additions are harmless. All correctly avoid electron-vite 6 beta and LSP-style monaco-languageclient.
- Object source layout: Plans 0 and 3 store one .dss per event (create.dss, step.dss, collision_obj_pipe.dss); Plans 1 and 2 store one file per object with `event` blocks. Endorse per-event files: it mirrors how GameMaker itself stores events, maps one-to-one onto the object editor's event list, gives trivial file:line diagnostics, and avoids the fragile 'scroll to or insert the matching block' text sync. Allow object-scoped helper functions via a functions.dss in the object folder (Plan 2's idea) rather than script-global only.
- Workstream fan-out and governance: Plan 0 freezes contracts in 2-3 days with WS1 in parallel on day 0, then fans out 7 streams; Plan 1 fans out 8 after 1-2 days; Plan 2 lets 9 agents start on v0 drafts while WS0 takes up to a week; Plan 3 tags phase0 after a claimed 4-6 hour Phase 0 and enforces ownership mechanically. Endorse Plan 0's 2-3 day budget with WS1 (toolchain install + hello ROM) running from hour zero, combined with Plan 3's mechanics (phase0 tag, CODEOWNERS + check-ownership hook, ADRs, kickoff prompts). Plan 3's 4-6 hour Phase 0 is not credible and Plan 2's week-long draft window invites churn.
- Repository location: Plans 0 and 3 move the repo to C:\dev\dsdude; Plan 1 keeps the canonical .git in OneDrive with worktrees elsewhere; Plan 2 never mentions it. Endorse the full move: node_modules, git objects and build/ under OneDrive's sync client cause lock and corruption problems on this machine, and worktrees still write through the main .git.
- Timeline and release scope: Plan 0 targets release 0.1 at week 12 with a dedicated integration/QA/release stream (NSIS, updater, licence bundle, py-desmume e2e, real-cart checklist); Plan 1 targets week 7-8 with a samples/QA stream; Plan 2 targets week 10 with no release owner; Plan 3 targets week 6 with no release owner. Endorse Plan 0's scope and calendar as the honest one, while adopting Plan 3's day-7/day-14 internal checkpoints to catch pipeline problems early.
- Real hardware: Plan 0 verifies on a real DS via Homebrew Menu at M6; Plan 3 tests at M3 if a cart exists; Plans 1 and 2 leave it to docs or post-v1. Endorse Plan 0 (with Plan 3's caveat that the user may not own a flashcart): NitroFS via argv/DLDI, sprite-per-scanline limits and card-read timing differ from emulators, and a 'GameMaker for DS' that only runs in melonDS will be reviewed the way DSGM was.
- VM vs transpile: all four choose a bytecode VM inside a prebuilt runtime ELF with Play doing only compile -> assets -> ndstool -> emulator, keeping a native-export transpiler as a later additive backend. Endorsed: for beginners this is decisive, since it means no compiler install for end users, sub-3-second Play, and runtime errors that say object/event/line instead of an ARM exception.
- Where the runtime's oracle lives: Plan 1 adds a TypeScript reference VM, Plan 3 a dsbc mini-interpreter, Plan 0 a host build 'with hardware stubs', and Plan 2 a portable C core with a formal dsd_platform.h seam and a full headless trace runner. Endorse Plan 2's design: the same C code runs on MSYS2 gcc and on the DS, so the oracle cannot drift from the product, and the core/platform split gives two parallel streams on the largest piece of work. A tiny TS mini-interpreter is acceptable only as an early compiler-test crutch.
- Object/event file layout: Plans 0 and 3 use one .dss file per event; Plans 1 and 2 use one file per object with `event name { }` blocks. Endorse per-event files: it mirrors GameMaker's event list exactly, removes a keyword from the language, makes the object editor a real file list, and makes error locations 'obj_bird / Step, line 3' without a scroll-to-block feature. Plan 1's object editor already syncs the event list, so the swap is cheap.
- Asset formats: Plans 0 and 3 shell out to grit -ftr (GRF) and load with grfLoadPath; Plan 1 invents .spr/.bgt/.tls with TS encoders/decoders; Plan 2 writes GRF in-house from its own quantizer/tiler. Endorse Plan 2's hybrid: the quantizer and tile packer are being written in TS anyway (all plans agree grit's palette handling confuses beginners), so writing the trivial GRF RIFF container keeps the runtime loader stock (grfLoadPath), drops grit and its DLLs from the end-user tools pack, and still allows grit as a golden cross-check in tests. Start M1 with grit behind Plan 3's ToolPaths seam if it speeds up the first boot.
- Live log capture: Plans 0 and 1 require node-pty (ConPTY) for unbuffered melonDS stdout; Plans 2 and 3 make it optional and accept batched pipes. Endorse Plans 2/3 for v1: batched logs plus Plan 1's on-device error screen and Plan 3's SELECT-toggled console overlay cover what a beginner needs, and node-pty is a native module that may not install here.
- Workstream split and integrator: Plan 0 has 9 streams with WS8 QA/release; Plan 1 has 9 with visual editors split from the shell; Plan 2 has 9 with the runtime split core/platform; Plan 3 has 7 with the strongest ownership tooling. Endorse Plan 1's split (shell vs visual editors; language service with docs; samples with QA) plus Plan 2's runtime core/platform split plus Plan 3's CODEOWNERS/check-ownership/ADR/kickoff-prompt mechanics; add Plan 0's explicit release-engineering ownership.
- Contract freeze timing: Plan 3 claims 4-6 hours, Plan 1 says 1-2 days, Plan 0 says 2-3 days, Plan 2 takes a week with others starting on drafts. Endorse 2-3 days with Plan 3's hard `phase0` tag: that is the realistic time to write builtins.json with docs, the bytecode spec, project schemas, fixtures and a hand-assembled hello, and it is still fast enough that the user can launch eight instances in the first week.
- v1 scope of tiles and language surface: Plans 1 and 2 include tilesets and tile painting in v1 and Plan 2 adds bitwise ops, ^^, ??, #macro and object-scoped functions; Plans 0 and 3 keep one background PNG per screen and a minimal operator set. Endorse the smaller surface (Plan 0/3) for the beginner milestone: Flappy, a top-down game and a platformer built from block objects need no tile painter, and every extra construct is another page a beginner must not have to read. Land tile painting and the extra operators after the human beginner test passes.
- Beginner acceptance gate: Plan 0 uses a human tester in under 2 hours, Plan 1 a recorded human usability session, Plan 3 a human in under 30 minutes with no terminal, and Plan 2 'a fresh agent session'. Endorse a human beginner (Plans 0/1/3) with Plan 3's 30-minute target; an agent walking a tutorial does not surface the confusions that matter.
- Execution strategy: all four pick a bytecode VM inside a prebuilt runtime ELF with ndstool -c repacking on Play, keeping transpile-to-C as a post-v1 export. Endorsed: end users never install a 300 MB toolchain, Play is sub-second, and runtime errors carry file:line.
- Runtime test oracle: Plan 0 and Plan 3 add a host build of the C VM with hardware stubs; Plan 2 makes the host build the single oracle via a portable core and dsd_platform.h seam with bit-identical integer math; Plan 1 has no host C build and relies on a TypeScript reference VM plus a conformance ROM run in the emulator; Plan 3 also adds a TS mini-interpreter. Endorse Plan 2's design: one C implementation compiled for host and DS, host traces as goldens, no separate TS VM (a third implementation of the semantics is a drift source, not a safety net).
- Runtime workstream decomposition: Plans 0, 1 and 3 give one instance the whole runtime (Plan 0 splits VM/engine only after M2); Plan 2 splits core and DS platform from day 0 with a selftest ROM. Endorse Plan 2's split: it halves the longest single-instance critical path and lets the platform layer be validated in melonDS before any bytecode runs.
- On-device asset format: Plans 0 and 3 run grit -ftr to produce GRF loaded by grfLoadPath; Plan 2 writes GRF in-house (no grit); Plan 1 invents custom .spr/.bgt/.tls formats with C loaders. Endorse GRF as the frozen on-device format with grit as a subprocess in v1 (proven loader path, GPL is fine across a process boundary) fed by an in-house RGB555 quantizer; an in-house GRF writer (Plan 2) is a fine v1.1 substitution behind the same contract. Reject custom formats: they double the loader work for no beginner-visible gain.
- Emulator and log capture: all four default to melonDS 1.1 with DeSmuME 0.9.13 as fallback and dual nocash output. Plans 0 and 1 prefer node-pty for unbuffered stdout; Plan 2 makes it optional; Plan 3 forbids native modules in v1 and adds an on-screen console overlay. Endorse Plan 3's stance given no VS C++ toolchain on this machine: batched pipes plus on-screen overlay in v1, node-pty only if prebuilds install cleanly.
- Workstream split and count: Plan 0 has 9 streams including separate language-service and QA/release; Plan 1 splits visual editors from the shell and merges language service with docs; Plan 2 separates build orchestration from toolchain/IDE and splits runtime core/platform; Plan 3 has 8 streams with a 'Learn' stream (docs + templates + language service). Endorse Plan 0's set with two grafts: split the runtime core/platform (Plan 2) and fold language service into a Learn stream (Plan 3) so peak concurrency stays around 8, which is what one person can realistically supervise.
- WS0 gate duration: Plan 3 says 4-6 hours, Plan 1 says 1-2 days, Plan 0 says 2-3 days, Plan 2 says one week (with streams starting on drafts). Endorse 2-3 days (Plan 0) structured as Plan 3's tagged phase0 walking skeleton; let streams start on v0 drafts as Plans 1 and 2 allow, but do not fan out before the hello ROM boots in melonDS from Node.
- Overall schedule: Plan 3 targets 6 weeks, Plan 1 5-8 weeks, Plan 2 10 weeks, Plan 0 12 weeks. Endorse Plan 0's 12-week horizon with Plan 3's day-3/day-7/day-14 checkpoint cadence inside it; the aggressive plans underestimate the C runtime (a full VM plus GameMaker engine on libnds is 4-6 instance-weeks, not 8-12 days).
- Contract change process: Plan 0 uses RFC PRs touching only specs and generated files; Plan 1 uses owner-only edits with a CHANGELOG line; Plan 2 uses PR-to-WS0 with an ABI hash bump; Plan 3 uses ADR + CHANGELOG + version bump + WS0-only merges enforced by a hook. Endorse Plan 3's process combined with Plan 2's ABI hash so incompatible bytecode is refused at load rather than silently misbehaving.
- QA and release ownership: Plan 0 has a dedicated WS8 (headless py-desmume e2e, Playwright, NSIS installer, updater, license bundle, real-cart checklist) starting at M2; Plan 1 folds QA into a samples stream; Plans 2 and 3 leave it to WS0's checkpoints and a late installer smoke. Endorse Plan 0's dedicated stream: an installer that works on a clean Windows 11 profile without MSYS2 is the difference between a demo and a product a beginner can use.
- Numeric model: all four choose int32 plus Q20.12 with Lua-style promotion and no doubles. Endorsed; graft Plan 2's 64-bit intermediates, debug overflow trap and checker warning, which the other plans omit.
