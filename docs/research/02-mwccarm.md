*Research report 2 of 6, produced 2026-09-24 during DSDude planning. Reference material only; see `docs/research/README.md`.*

# Feasibility of CodeWarrior (mwccarm) + ds-decomp (dsd) as the build backend for a greenfield DS homebrew IDE

## 0. Verdict up front

- **Primary backend: BlocksDS (GCC `arm-none-eabi` + libnds, Zlib/MPL-2.0), installed into the existing MSYS2 via the Wonderful Toolchain (`wf-pacman -S blocksds-toolchain`).** It ships everything the CodeWarrior route lacks: crt0, MPU/TCM setup, an IRQ dispatcher, a maintained ARM7 core (touch, sound, RTC, power, storage), `ndstool` for ROM packing, `grit` for graphics conversion, and a Windows-native install path. The ROMs it produces boot in DeSmuME 0.9.13 (already downloaded) and melonDS.
- **CodeWarrior (mwccarm/mwasmarm/mwldarm): drop as an IDE backend.** Mechanically it works (proved below), but it is proprietary and unshippable, 32-bit Windows-only, ships with **no target headers and no C library**, has no ARM7 story, and would require an 8–14 person-week from-scratch HAL before the first sprite moves. At most keep it as an undocumented "expert compiler" experiment, never as something the IDE depends on.
- **dsd (ds-decomp 0.12.1 / ds-rom 0.8.0): no role in the build pipeline.** `dsd rom extract/build/config` exist to re-link *decompiled retail games*; they require a NitroSDK-style ARM9 footer (`nitrocode 0xDEC00621`), a 0x4000-byte header, an FNT and a banner. A homebrew ROM built by us fails at each of those checks (verified). Optional secondary role: an "Import from retail ROM" / "ROM inspector" feature (extract `files/`, banner PNG, logo PNG from a NitroSDK-built game), clearly fenced off as a ROM-hacking convenience.

## 1. What is on the machine (verified)

- `mwccarm/2.0/sp1/mwccarm.exe` reports "Metrowerks C/C++ for Embedded ARM, Version 3.0 build 123, Copyright (c) 2006 Freescale Semiconductor". All exes and `lmgr8c.dll` are **PE32 i386 (machine 0x14c)**, i.e. 32-bit Windows binaries. They run on Windows 11 x64 via WOW64; on Linux/macOS they need Wine or MetroSkrew (below).
- The bundle contains **no ARM-side headers and no ARM-side C library**: `find mwccarm -iname '*.h' -o -iname '*.a' -o -iname '*.lib'` returns only `mwccarm/stub_libs/libcf.a`, which is 8 bytes (`!<arch>\n`). `MSL_All-DLL80_x86.dll` is the compiler's *host* runtime, not the target MSL. So even `#include <stdint.h>` or `memcpy` must be written by us.
- `mwccarm/2.0/base/ARM9-*.lcf.template` are NitroSDK `makelcf` templates carrying the header "Copyright 2003-2005 Nintendo … proprietary information of Nintendo … may not be disclosed to third parties or copied". They show the NitroSDK static-module layout (`libsyscall.a`, `crt0.o`, `SDK_STATIC_*`, `SDK_OVERLAYTABLE_DIGEST`, `ITCM__` 0x8000 bytes, `DTCM__` 0x4000 bytes) but are not usable in a redistributable product.
- `mwccarm/1.2/license.dat` is a FlexLM file titled "CodeWarrior Development Studio for Nintendo DS v1.1" with four `FEATURE … permanent uncounted … HOSTID=ANY` lines. That is not a vendor-issued node-locked license; treat it as unlicensed use.
- `mwldarm` (2.0 build 82) options that matter: `-m symbol` sets the entry point, `-map` writes `.xMAP`, `-nostdlib`, `-application|-library`, `-srec`/`-xrec` (S-record/Intel HEX). There is **no raw-binary output**; the local `C:\devkitPro\devkitARM\bin\arm-none-eabi-objcopy` fills that gap.

## 2. Hands-on proof: mwccarm → mwldarm → objcopy → .nds

Done in the scratchpad (`…\scratchpad\exp\`), with `LM_LICENSE_FILE` pointing at `mwccarm\1.2\license.dat`:

```
mwccarm -proc arm946e -O2 -nostdinc -msgstyle gcc -c crt0.c -o crt0.o
mwccarm -proc arm946e -O2 -nostdinc -msgstyle gcc -c main.c  -o main.o
mwldarm -proc arm946e -nostdlib -m _start -map -o arm9.elf crt0.o main.o arm9.lcf
arm-none-eabi-objcopy -O binary arm9.elf arm9.bin      # 148 bytes
```

- `crt0.c` used CodeWarrior's `asm void _start(void) { … }` function-level assembler (sets IME=0, `sp=0x023FE000`, `bl main`, spin). `main.c` sets `POWCNT1=0x8003`, `VRAMCNT_A=0x80`, `DISPCNT=0x00020000` and fills LCDC VRAM at `0x06800000` with a gradient — no headers, no libc.
- `arm9.lcf` was 11 lines: `MEMORY { main (RWX) : ORIGIN = 0x02000000, LENGTH = 0 } SECTIONS { .main : { ALIGNALL(4); crt0.o (.text) main.o (.text) … } > main }`. `objdump -f` confirms `start address 0x02000000`, `_start` at 0x02000000, `main` at 0x02000020.
- A 60-line Python script wrote the GBATEK header (title, gamecode `####`, ARM9/ARM7 offsets/entries/sizes, port settings 0x00586000/0x001808F8, secure-area delay 0x051E, logo CRC 0xCF56, header CRC-16/MODBUS over bytes 0..0x15D) plus a stub ARM7 (`0xEAFFFFFE`, `b .`, loaded at 0x03800000) and produced `dsdude_test.nds` (0x200 header, ARM9 at 0x200, 1,536 bytes) and `hdr4000_full.nds` (0x4000 header, ARM9 at 0x8000, minimal FNT + v1 banner, 36,864 bytes).
- **Not yet booted in an emulator** (no headless DeSmuME); the header layout follows exactly what melonDS/DeSmuME accept (section 3). This experiment took under an hour and is the *entire* value CodeWarrior brings: a working C compiler for ARM946E-S. Everything above the compiler is missing.

## 3. What a bootable .nds actually needs (GBATEK + emulator sources)

**Header (0x000–0x1FF, GBATEK "DS Cartridge Header")**: title (12), gamecode (4), makercode (2), unitcode, seed select, capacity, flags; `0x20` ARM9 ROM offset (retail: 0x4000+), `0x24` ARM9 entry and `0x28` RAM address (both in 0x2000000–0x23BFE00), `0x2C` size (max 0x3BFE00); `0x30–0x3C` the same for ARM7 (RAM/entry in 0x2000000–0x23BFE00 **or** 0x37F8000–0x3807E00); `0x40–0x4C` FNT/FAT offset+size; `0x50–0x5C` overlay tables; `0x60/0x64` cart port settings; `0x68` banner offset (0 = none); `0x6C` secure-area CRC; `0x6E` secure-area delay; `0x70/0x74` autoload hooks (NitroSDK-specific); `0x80` used ROM size; `0x84` header size; `0xC0` Nintendo logo (156 bytes, compressed bitmap); `0x15C` logo CRC (fixed CF56h); `0x15E` header CRC-16 over 0x000–0x15D.

**Secure area**: exists only if the ARM9 ROM offset is in 0x4000–0x7FFF; its first 2 KB are KEY1-encrypted and start with `encryObj`. GBATEK: setting the ARM9 offset to ≥0x8000 "eliminates the Secure Area entirely … works on real hardware and is used by Nintendo's devkit"; ARM9 at <0x4000 is "silently skipped" by the BIOS but is exactly the classic homebrew convention (`ndstool -h 0x200`). BlocksDS reserves a 2 KB `.secure` pad at the start of the ARM9 binary so that placing it at 0x4000 is harmless.

**Emulator checks (from source)**:
- melonDS `NDSCart.cpp::ValidateROM` only checks `ARM9ROMOffset >= 0x200` and that ARM9/ARM7 offset+size fit in the file; `NDS_Header.h::IsHomebrew()` is `ARM9ROMOffset < 0x4000 || GameCode == "####"`. No header-CRC, no logo check. It re-encrypts the secure area only when ARM9 offset is in 0x4000–0x7FFF.
- DeSmuME `NDSSystem.cpp` never validates header CRC or logo; `isHomebrew()` is `(ARM9src < 0x4000 && logo != Nintendo's) || gameCode == "####"`.
- Real hardware: the BIOS checks only the CF56h value; the *firmware* validates the logo bitmap when booting a physical cart. Flashcart homebrew menus copy ARM9/ARM7 straight to RAM and jump, so the logo is irrelevant there; a correct header CRC and a real logo are still cheap to emit (ndstool computes both: `CalcHeaderCRC` over 0x15E bytes, `CalcLogoCRC` over 156 bytes at 0xC0).

**Memory map / load addresses**: main RAM 0x02000000 (4 MB); ITCM 32 KB at 0x00000000, mirrored (libnds links it at 0x01000000); DTCM 16 KB, base moveable via CP15 (libnds: 0x02FF4000; NitroSDK: 0x027E0000); shared WRAM 32 KB at 0x03000000 split by WRAMCNT; ARM7 WRAM 64 KB at 0x03800000 (BlocksDS ARM7 links at `0x03800000 - __shared_wram_size`, with a bounce copy from EWRAM 0x02380000); LCDC VRAM 0x06800000.

**Minimal crt0 (what BlocksDS `sys/crts/ds_arm9_crt0.s` does, MPL-2.0)**: IME=0; temporary SVC/System stacks; `__libnds_mpu_setup` (CP15: disable/flush caches, `DTCM base = __dtcm_start`, ITCM enabled 32 MB-mirrored, eight protection regions covering I/O 0x04000000, BIOS, alt vectors, DTCM, ITCM, GBA slot, cacheable/non-cacheable main RAM; caches on); per-mode stacks `__sp_irq/__sp_svc/__sp_usr` in DTCM; a **five-step IPCSYNC handshake with the ARM7** (0→9, A→B, C→D, SCFG_A9ROM, 7); copy ITCM/DTCM from LMA to VMA; clear BSS/SBSS; DSi extras; flush caches; set heap; jump to `main` through the cothread scheduler. A CodeWarrior HAL must reproduce all of this in mwasmarm/inline asm (CP15 via `mcr`), plus the IRQ vector at DTCM top (`__irq_vector = __dtcm_top - 4`).

**ARM7 is not optional**: the header must reference an ARM7 program, and the ARM7 is the only CPU that can read the touchscreen, X/Y buttons, RTC, firmware user settings, power management, and drive the sound hardware. The BlocksDS default core (`sys/arm7/main_core/source/main.c`, Zlib, 137 lines) does: `enableSound(); readUserSettings(); ledBlink(0); touchInit(); irqInit(); fifoInit(); installSoundFIFO(); installSystemFIFO()` (sleep, storage/DLDI, firmware), `installCameraFIFO()` on DSi, optional `mmInstall(FIFO_MAXMOD)` or LibXM7, `setPowerButtonCB`, `initClockIRQTimer`, and a VBlank handler calling `inputGetAndSend()`; it exits on the power button or SELECT+START+L+R. Prebuilt variants: `minimal`, `dswifi`, `maxmod`, `libxm7`, `dswifi_maxmod`, `dswifi_libxm7` (+ `_debug`). A CodeWarrior ARM9 could in principle ship the BlocksDS ARM7 binary (Zlib allows it) but would then have to re-implement libnds's FIFO message protocol on the ARM9 side — a hidden second HAL.

## 4. Open NitroSDK-compatible headers/runtime: what exists and what is legal

- **`ntrtwl/NitroSDK`** (GitHub) is what pret's `pokeplatinum` pulls in via `subprojects/NitroSDK.wrap` (`url = https://github.com/ntrtwl/NitroSDK.git`, directory `NitroSDK-4.2.30001`); its `include/nitro/` has the genuine `os.h, gx.h, fs.h, snd.h, pad.h, mi.h, pxi.h, card.h, wm.h, mb.h, memorymap.h, dtcm_begin.h…`. It has **no LICENSE file** and is Nintendo's proprietary SDK 4.2 (the same code family whose LCF templates in your folder carry Nintendo's non-disclosure notice). Decomp projects use it under community tolerance; an IDE that bundles or auto-downloads it would be redistributing Nintendo's SDK. Not usable.
- **`cybervisi0n/libntr`** (MIT) is a NitroSDK-API-compatible reimplementation whose stated purpose is PC ports of decomps (OpenGL 4.2 3D, simulated 2D, netplay); it lists `arm` (DS hardware) as a meson target but is early-stage (4 stars, 96 commits), meson/GCC-oriented, and was never built with CodeWarrior. Interesting to watch, not a foundation.
- **libnds/BlocksDS** is the only mature, permissively-licensed DS runtime: libnds is Zlib (FatFs separately licensed), BlocksDS crts are MPL-2.0, the ARM7 core Zlib. Size for scale: `source/arm9` 19,168 lines of C/asm, `source/arm7` 5,531, `source/common` 5,989, headers 22,050 lines. It is GCC-only (GNU asm syntax, `__attribute__`, linker-script symbols); porting it to CodeWarrior is a rewrite, not a port.
- No CodeWarrior-compatible open HAL for DS exists.

## 5. What dsd / ds-rom really do (from source, ds-decomp 0.12.1, ds-rom 0.8.0)

- `dsd rom extract --rom X.nds --output-path DIR [--arm7-bios]` writes `config.yaml` referencing: `header.yaml` (title, gamecode, makercode, unitcode, seed_select, ds_flags, rom_version, autostart, normal/key1_cmd_setting, secure_area_delay, rom_nand_end, rw_nand_end, has_arm9_build_info_offset), `header_logo` PNG, `arm9/arm9.bin` + `arm9/arm9.yaml` (`offsets: {base_address, entry_function, build_info, autoload_callback, overlay_signatures}`, `encrypted`, `compressed`, `build_info: {bss_start, bss_end, sdk_version}`), `arm9/itcm.bin|yaml`, `arm9/dtcm.bin|yaml`, `unk_autoload_N`, `arm9_overlays/overlays.yaml`, `arm7/arm7.bin` + `arm7/arm7.yaml` (`base_address, entry_function, build_info, autoload_callback`), `banner/banner.yaml` (+ bitmap/palette PNGs), `files/`, `path_order`, `alignment`, `padding`, optional `arm9_hmac_sha1_key`, `multiboot_signature`.
- `dsd rom build --config DIR/config.yaml --rom out.nds` reloads that tree, rebuilds FNT/FAT/banner, recompresses ARM9 (unless `--no-compress`), regenerates the logo from PNG, logo CRC and header CRC. The ARM7 BIOS is required **only** when `arm9.yaml` says `encrypted: true` (it derives the Blowfish key from the BIOS to re-encrypt the secure area).
- `dsd rom config --elf final.o --config dsd/config.yaml` is a decomp re-link step: it loads the *original* extract directory (for header, banner, ARM7, files), then reads from the mwldarm ELF the sections `ARM9`, `ITCM`, `DTCM`, `AUTOLOAD_n`, `OV###` and symbols `Entry`, `BuildInfo`, `AutoloadCallback`, `OverlaySignatures`, `OV###_CTOR_START/END`, and rewrites `arm9.yaml`, autoload YAMLs, `arm9_overlays.yaml`, `rom_config.yaml`. It cannot run without a prior `rom extract` of a real game.
- `dsd lcf` fills `assets/arm9.lcf.template`: one `MEMORY` region per module with `ORIGIN` and `> output_file`, `KEEP_SECTION { .init, .ctor, .exceptix }`, per-section start/end symbols, and writes an objects list for mwldarm. It is driven by `delinks.txt`/`symbols.txt` from `dsd init`, not by a user project.
- **Empirical gate for homebrew**: feeding my ROMs to `dsd rom extract` failed successively with `expected 0x4000 bytes for header but had only 0x600`, then `file name table must be at least 8 bytes long`, then `unknown banner version …`, and finally — with a 0x4000 header, ARM9 at 0x8000, a valid 8-byte FNT and a v1 banner — `expected nitrocode 0xdec00621 in ARM9 footer but got 0x0`. ds-rom's `BuildInfo` parser insists on the NitroSDK "nitrocode" footer and autoload-info list. Homebrew ROMs (ndstool or ours) will never pass, so dsd cannot package or even inspect our own output. It *can* extract retail NitroSDK games, which is the only role left for it.

## 6. Licensing / distribution reality of CodeWarrior

- Metrowerks (a Freescale subsidiary; Freescale is now NXP) was Nintendo's official DS toolchain vendor from 2004; Nintendo distributed the kits to roughly 100 licensed developers. It was never sold publicly and is discontinued.
- Today's copies come from the DS Decompilation Discord (`mwccarm.zip`, the exact layout in your folder) and from the Internet Archive item `cw_consoles` (5.8 GB; uploader: "these are the full versions; however they install in trial mode. You will need a corresponding license"). Decomp READMEs state plainly that mwccarm is "proprietary and not redistributable". The sm64ds-decomp notes even avoid `license.dat` altogether ("these builds run without it") — worth testing on your copy, since your orchestrator found the compiler *hangs* without `LM_LICENSE_FILE`; the difference may be version-specific.
- Consequence for an IDE: it cannot ship, download, or link to the compiler; every user would have to find it on Discord and configure a license. That alone disqualifies it as the default backend for a beginner-oriented product.
- Cross-platform: `mid-kid/metroskrew` (v0.1.2, last commit 2025-05-30) relinks the PE binaries into native 32-bit x86 Linux executables (meson asserts `cpu_family() == 'x86'`; optional `wine_wrap`). It works for decomp CI but is another fragile layer; GCC has none of this.

## 7. Effort estimate

| Path | Scope | Estimate |
|---|---|---|
| **From-scratch CodeWarrior HAL, MVP** | crt0 + CP15/TCM/MPU, IRQ dispatcher, BIOS SWI wrappers, DMA/timers, 2D BG/OBJ/VRAM helpers, keys, mini libc (memcpy/memset/printf-lite/malloc, stdint/stdarg shims for `-nostdinc`), an ARM7 program with touch/X-Y/sound/RTC/power and a custom FIFO protocol, ROM filesystem reader (card reads + DLDI hook), ROM packer, LCF templates | 8–14 person-weeks for someone who already knows the DS; more when every subsystem must be validated on real hardware/emulators without reference code |
| **Parity with libnds/BlocksDS** | + maxmod-class sound mixer, 3D, console, DSi mode, Wi-Fi, FAT/SD, exceptions, examples | 6–12 person-months |
| **libnds/BlocksDS** | HAL: 0. Engine layer (rooms/objects/events/sprites/tilemaps/audio/input bindings for your GML-like language): 1–2 person-weeks, plus install scripting (`wf-pacman`) and a Makefile template | ~2 person-weeks total to first playable |

Multiplying the CodeWarrior path across several parallel Claude Code instances does not help: the HAL is a serial, hardware-validation-bound task, whereas the libnds path parallelises cleanly (engine, transpiler, IDE UI, asset pipeline, build/play runner).

## 8. Recommended shape of the pipeline

`GML-like source → transpiler (Node/Python) → C → BlocksDS make (arm-none-eabi-gcc + libnds, default ARM7 core with maxmod) → ndstool (header 0x4000, banner from PNG, nitroFS assets) → Play button launches DeSmuME 0.9.13 (or melonDS, whose cart-loading is stricter and closer to hardware)`. Keep `dsd-windows-x86_64.exe` in a `tools/` folder for an optional "Import assets from a retail ROM" panel and nothing else.

## Recommendations
- Adopt BlocksDS as the sole build backend: from the existing MSYS2 UCRT64 shell run `pacman -S base-devel ca-certificates`, install the Wonderful Toolchain per https://wonderful.asie.pl/wiki/doku.php?id=getting_started, then `wf-pacman -Syu wf-tools && wf-config repo enable blocksds && wf-pacman -Syu && wf-pacman -S blocksds-toolchain` (optional `blocksds-docs`); build from the 'Wonderful Toolchain Shell' or replicate its BLOCKSDS/WONDERFUL_TOOLCHAIN env vars in the IDE's build runner.
- Drop mwccarm/mwasmarm/mwldarm as an IDE backend. Do not bundle, auto-download, or document it in the product; if you personally want to keep experimenting, the working recipe is in the scratchpad `exp/` folder (crt0.c, main.c, arm9.lcf, mk_full.py) and needs only `LM_LICENSE_FILE` plus `arm-none-eabi-objcopy`.
- Give dsd at most an optional 'Import from retail ROM' / 'ROM inspector' feature that shells out to `dsd rom extract --rom X.nds --output-path DIR` and reads the resulting `config.yaml`, `banner/`, `header_logo` PNG and `files/`; state in the UI that it only works on NitroSDK-built commercial ROMs (it rejects homebrew with 'expected nitrocode 0xdec00621') and that asset formats (NCGR/NCLR/NSCR/NARC/SDAT) need separate parsers. Do not build the pipeline around it.
- Use BlocksDS's `ndstool` for ROM packing (header size 0x4000, gamecode '####', banner icon from a 32x32 PNG, nitroFS directory for assets) instead of a custom packer; it writes a valid header CRC, logo and logo CRC, which covers emulators, flashcart menus and real carts.
- Ship the BlocksDS default ARM7 core variant `maxmod` (sound + touch + RTC + power) unless Wi-Fi is needed (`dswifi_maxmod`); never write a custom ARM7 for v1.
- Play button: launch DeSmuME_0.9.13_x64.exe with the ROM path as argv[1]; consider offering melonDS as the recommended emulator because its cart loader (`ValidateROM`, KEY1 handling) is closer to hardware; both accept ndstool ROMs without any secure area.
- Split the IDE into parallel workstreams that the libnds choice makes independent: (1) toolchain bootstrap + build/play runner (MSYS2/wf-pacman scripts, Makefile template, ndstool, emulator launch); (2) GML-like language front end (parser, type checker, C transpiler emitting calls into a fixed engine ABI); (3) C runtime engine on libnds (rooms, objects/instances, event dispatch, sprites/OBJ, tilemaps/BG, collision, maxmod audio, input incl. touch); (4) asset pipeline (PNG to tiles/palettes via `grit`, sound conversion, nitroFS packing); (5) IDE UI (editor, project tree, room editor, console for build output). Define the engine ABI header and the project-file JSON schema first so instances can proceed concurrently.
- Verify one thing early with the user present: boot `scratchpad/exp/dsdude_test.nds` and `hdr4000_full.nds` in DeSmuME to confirm the header layout empirically (the top screen should show a colour gradient); this also validates the Play-button launch command.
- Keep the Nintendo LCF templates and any NitroSDK material out of the repository and out of the IDE; they carry Nintendo's proprietary notice and cannot be redistributed.
